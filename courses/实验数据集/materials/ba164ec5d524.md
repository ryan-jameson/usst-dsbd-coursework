课程设计：拍卖会桌面游戏数据库设计
一、研究背景与目标
拍卖会游戏是以介绍优秀文化藏品，体验拍卖过程的多玩家桌面游戏。若某游戏公司计划实现此游戏的网络游玩和运营，设计建立游戏数据库是关键的步骤。
拍卖会游戏的玩家设置为八组玩家(本金均为100)，每组3-4人，其中1人为来自其他组的间谍。拍卖中共有8件藏品，藏品应设置起拍价格、初始价值、增量系数。
游戏分为四轮次：
第一轮：竞拍A、C、E、G四种藏品，每组可向1种藏品出价；
第二轮：竞拍B、D、F、H四种藏品，每组可向1种藏品出价；
第三轮：竞拍全部未被拍下的藏品，每组可向2种藏品出价；
第四轮：竞拍全部未被拍下的藏品，每组可向2种藏品出价
出价规则：出价阶段，每组指定一名成员非公开出价，出价不低于起拍价格；非间谍玩家仅能操作本组本轮的竞拍数据；每位成员仅能执行一次常规出价任务；
间谍规则：间谍与身份号码指定的所属组共享胜利条件；间谍在出价时，可以操作所在组和所属组的本轮竞拍数据；
结算规则：每轮所有玩家出价完毕后进入结算；若仅有1组玩家出价，则以起拍价格获得藏品；若有2组玩家出价，则公开两组的首次报价，由报价高的玩家从两组各自指定任意一名成员非公开出价，出价不低于首次报价，价高者竞拍成功；若有3组及以上玩家出价，则触发冲突，出价无效，藏品价值提升；
获胜规则：四轮游戏结束后，获得藏品具有最高价值总分的组获胜；若多组获得价值总分相同，则剩余资产最高者获胜；
请通过设计并建立游戏数据库，达到以下要求：
1、至少对游戏信息、玩家信息、游戏过程进行数据记录与管理；
2、优化数据库达到2NF，避免过度的数据冗余；
二、E-R图与关系模式
本数据库设计包含 5 个关系模式。以下符号约定：加粗表示主键，斜体表示外键。相关E-R图如图19所示。
1. 游戏场次 (Game_Sessions)
模式定义：Game_Sessions (session_id, start_time, status)
设计说明：作为系统的根实体，用于区分不同的游戏对局。status 字段采用枚举类型（WAITING/ROUND_1/... /FINISHED），控制游戏周期的流转。
2. 队伍信息 (Teams)
模式定义：Teams (team_id, session_id, team_name, balance)
设计说明：队伍是游戏的资产持有主体。存在 session_id → team_id 的 1:n 关系，表示一场游戏包含多个队伍。balance（本金）是判定出价能力的关键属性。
3. 玩家信息 (Players)
模式定义：Players (player_id, team_id, true_team_id, player_name, is_spy, has_acted_this_round)
设计说明：因为间谍身份的存在，这里设计双重归属，表内包含两个指向 Teams 的外键。其中team_id表示玩家当前所在的“物理组”（操作权限归属），而true_team_id表示玩家效忠的“真实组”（胜利条件归属）。通过这两个外键的异同（team_id != true_team_id），在数据层面实现了“间谍”逻辑。
4. 藏品信息 (Items)
模式定义：Items (item_id, session_id, item_code, item_name, base_price, current_value, increment_coeff, owner_team_id, status)
设计说明：记录藏品的静态属性（如代号、起拍价）和动态属性（如当前价值、归属）。owner_team_id 允许为空（NULL），表示藏品尚未被拍下；非空时指向 Teams 表，表示归属权转移。
5. 竞拍记录 (Bids)
模式定义：Bids (bid_id, session_id, round_num, item_id, team_id, player_id, bid_amount, phase_type, bid_time)
设计说明：这是 E-R 图中多对多关系的实体化表现。它连接了 Players（执行者）、Teams（名义出价方）、Items（竞价藏品）。该表记录了游戏全过程的所有操作流水，是结算和冲突判定的数据源。

三、任务的完成
为了完成这项实验，我设计了三个核心属性：
1. Players.true_team_id (真实归属组ID)
设计原因：为了满足“间谍与身份号码指定的所属组共享胜利条件”这一复杂规则。如果仅设计一个 is_spy (布尔值) 字段，系统只能知道某人是间谍，但无法知道他要把情报或利益输送给谁。必须引入 true_team_id 作为外键指向 Teams 表。比如在我们的脚本中，玩家 A_Spy_from_B 的设定是 team_id = @t1 (身在A组)，但 true_team_id = @t2 (心在B组)。且在当他出价时，出现约束，系统检查 team_id，允许他操作 A 组的数据。最后当游戏结束计算总分时，系统根据 true_team_id 将他的贡献（如果有特殊设定）或胜利状态归算给 B 组。
2. Items.increment_coeff (增量系数)
设计原因： 题目要求“若有3组及以上玩家出价，则触发冲突，出价无效，藏品价值提升”。为了增加游戏的策略深度，不同藏品（如 A级宝物 vs H级杂项）的升值幅度不应相同。将“升值幅度”参数化存储在数据库中，而非硬编码在程序里，体现了数据驱动的设计思想。比如在第一轮和第三轮的模拟中，藏品G 多次遭遇 A、D、F 组的混战。我们的 SQL 逻辑是：current_value = current_value + (竞拍人数 * increment_coeff)。如果 G 的系数设定为 30，每次冲突有3人参与，价值就暴涨 90。如果是系数为 5 的 H 藏品，同样的冲突只会升值 15。这直接导致了第四轮 B 组即便花 50 块买下 G 也是血赚的局面。
3. Bids.phase_type (出价阶段类型)
设计原因： 游戏规则包含复杂的流程控制：“首次报价” -> “冲突检测” -> “公开报价” -> “二次出价（对决）”。 如果不区分出价阶段，数据库中就会出现针对同一轮、同一物品的多个出价记录，导致系统无法区分哪个是“引发冲突的原始出价”，哪个是“解决冲突的最终出价”。因此引入枚举字段 phase_type ('INITIAL', 'DUEL')。根据AI模拟拍卖，在第二轮 藏品B 的争夺中：T5 和 T6 首先进行了 INITIAL 出价（均为 80），系统识别出 2 条 INITIAL 记录 -> 判定触发对决。随后 T5 追加了一个 DUEL 出价（90）。结算脚本只会选取 phase_type = 'DUEL' 的最高价作为最终成交价，而忽略之前的 80 块。若没有这个字段，SUM 或 MAX 操作就会发生逻辑错误，最终全流程代码如附录所示。

四、总结与讨论
在本次“拍卖会桌面游戏”的数据库设计与实现过程中，我主要面临了业务逻辑复杂化与数据模型规范化之间的冲突，具体表现为以下两点：
困难一：特殊身份（间谍）的逻辑表达
其中游戏规则要求“间谍”既受当前所在组的操作限制，又与其真实效忠的组共享胜利条件。若仅使用简单的布尔值标记，无法在数据库层面体现“身在曹营心在汉”的复杂归属关系。
因此我这里利用关系模型中的外键机制解决此问题。我在 Players 表中设计了双重外键：team_id 关联物理所在组，true_team_id 关联真实效忠组。通过这两个属性的一致性判断（team_id = true_team_id），既满足了参照完整性，又灵活实现了游戏逻辑。
困难二：多轮次竞价与冲突处理的数据记录
因为游戏包含多轮次、多阶段（初始出价/对决出价）以及多人冲突导致的流拍。如果将出价信息直接记录在 Items 表中，会导致属性非原子化或大量重复数据。
因此我决定将“出价”这一动作实体化，设计了独立的 Bids 关系模式。引入 phase_type（枚举：INITIAL/DUEL）和 round_num 属性，精确记录每一次博弈的状态。我认为这里我将多对多关系转化为了一对多关系，解决存储问题，也为后续计算“藏品增值系数”提供了完整的数据源。
纵观我这个实验来说，在设计初期，我曾考虑将“当前最高出价”直接放在 Items 表中。但分析发现，“出价”依赖于 (session_id, item_id, team_id) 的组合，而 Items 表的主键是 item_id。如果强行合并，会产生部分依赖，导致数据冗余和更新异常。因此通过将 Bids 表独立，我确保了 Items 表符合 2NF 甚至 3NF。不仅节省了存储空间，更重要的是保证了“藏品属性”与“竞拍行为”的数据解耦，使得我们在更新藏品价值（根据人数和系数）时，不会破坏表结构。
而在脚本编写中，我深刻体会到外键约束的重要性。例如，Teams 表的 session_id 必须存在于 Game_Sessions 表中。在模拟清空数据时，必须先通过 SET FOREIGN_KEY_CHECKS = 0 关闭检查才能截断表，这反向证明了数据库在日常操作中是如何严密保护数据引用关系的。
本次课程设计也让我对 “E-R图向关系模式的转换” 以及 “视图（View）的应用” 有了更深的体会。在实验中，我将 Players 与 Teams 之间抽象的“拥有”和“效忠”关系，转化为具体的数据库表结构。我意识到，E-R 图不仅是画图，更是对业务规则的深度梳理；关系模式则是对这些规则的数学化定义。
而在实验的最后阶段，为了解决复杂的胜负判定（余额 + 藏品动态价值），我使用了视图结合窗口函数（RANK）。这让我明白，数据库不仅仅是数据的存储仓库，更是强大的计算引擎。通过视图封装逻辑，既简化了应用层的查询负担，又保证了排名算法的一致性。
总的来说，本次实验通过构建一个包含间谍机制、价值动态叠加的拍卖系统，让我将《数据库原理》中的理论知识（特别是范式理论和完整性约束）真正落地，体会到了设计优良的数据库模式对于处理复杂业务逻辑的决定性作用。

CREATE DATABASE IF NOT EXISTS AuctionGameDB DEFAULT CHARSET utf8mb4;
USE AuctionGameDB;

-- 1. 游戏场次表 (Game_Sessions) 用于记录每一局游戏的全局状态
CREATE TABLE game_sessions (
    session_id INT AUTO_INCREMENT PRIMARY KEY COMMENT '游戏场次ID',
    start_time DATETIME DEFAULT CURRENT_TIMESTAMP COMMENT '开始时间',
    status ENUM('WAITING', 'ROUND_1', 'ROUND_2', 'ROUND_3', 'ROUND_4', 'FINISHED') DEFAULT 'WAITING' COMMENT '当前游戏状态');
-- 2. 队伍表 (Teams) 记录玩家组的信息和资金
CREATE TABLE teams (
    team_id INT AUTO_INCREMENT PRIMARY KEY,
    session_id INT NOT NULL COMMENT '所属游戏场次',
    team_name VARCHAR(50) NOT NULL COMMENT '组名',
    balance DECIMAL(10, 2) DEFAULT 100.00 COMMENT '当前本金',
    FOREIGN KEY (session_id) REFERENCES game_sessions(session_id) ON DELETE CASCADE
);

-- 3. 玩家表 (Players) 核心设计：通过 true_team_id 实现间谍逻辑
CREATE TABLE players (
    player_id INT AUTO_INCREMENT PRIMARY KEY,
    team_id INT NOT NULL COMMENT '当前所在的物理组',
    true_team_id INT NOT NULL COMMENT '真实效忠的组(用于间谍判定)',
    player_name VARCHAR(50) NOT NULL,
    is_spy BOOLEAN DEFAULT FALSE COMMENT '是否是间谍标记',
    has_acted_this_round BOOLEAN DEFAULT FALSE COMMENT '本局是否已行动(每人限一次)',
    FOREIGN KEY (team_id) REFERENCES teams(team_id),
    FOREIGN KEY (true_team_id) REFERENCES teams(team_id)
);

-- 4. 藏品表 (Items) 记录藏品属性和状态
CREATE TABLE items (
    item_id INT AUTO_INCREMENT PRIMARY KEY,
    session_id INT NOT NULL,
    item_code CHAR(1) NOT NULL COMMENT '藏品代号 A-H',
    item_name VARCHAR(100) COMMENT '藏品名称',
    base_price DECIMAL(10, 2) NOT NULL COMMENT '起拍价格',
    current_value DECIMAL(10, 2) NOT NULL COMMENT '当前价值(初始价值)',
    increment_coeff DECIMAL(5, 2) DEFAULT 1.5 COMMENT '增量系数(冲突时价值提升倍数)',
    owner_team_id INT DEFAULT NULL COMMENT '归属队伍，NULL为未被拍下',
    status ENUM('AVAILABLE', 'SOLD', 'CONFLICT_LOCKED') DEFAULT 'AVAILABLE',
    FOREIGN KEY (session_id) REFERENCES game_sessions(session_id),
    FOREIGN KEY (owner_team_id) REFERENCES teams(team_id)
);
-- 5. 竞拍记录表 (Bids) 记录所有出价行为，用于结算
CREATE TABLE bids (
    bid_id INT AUTO_INCREMENT PRIMARY KEY,
    session_id INT NOT NULL,
    round_num INT NOT NULL COMMENT '轮次: 1-4',
    phase_type ENUM('INITIAL', 'DUEL') DEFAULT 'INITIAL' COMMENT '出价阶段：初始出价或冲突对决',
    item_id INT NOT NULL,
    team_id INT NOT NULL COMMENT '名义出价组',
    player_id INT NOT NULL COMMENT '实际操作人',
    bid_amount DECIMAL(10, 2) NOT NULL,
    bid_time TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (session_id) REFERENCES game_sessions(session_id),
    FOREIGN KEY (item_id) REFERENCES items(item_id),
    FOREIGN KEY (team_id) REFERENCES teams(team_id),
    FOREIGN KEY (player_id) REFERENCES players(player_id)
);

-- 3. 第一轮 价值核算 (Value Calculation)
-- ==========================================
-- 规则：当前价值 = 初始价值 + (本轮竞拍人数 * 系数)
-- A (20系数): T1参与 -> 100 + 1*20 = 120
-- C (30系数): T2, T3参与 -> 80 + 2*30 = 140
-- E (10系数): T4, T5, T6参与 -> 80 + 3*10 = 110
UPDATE items i
JOIN (
    SELECT item_id, COUNT(DISTINCT team_id) as team_count
    FROM bids 
    WHERE session_id = @s_id AND round_num = 1
    GROUP BY item_id
) b ON i.item_id = b.item_id
SET i.current_value = i.current_value + (b.team_count * i.increment_coeff);

--- 如果视图已存在则替换，不存在则创建
CREATE OR REPLACE VIEW view_game_results AS
SELECT 
    t.session_id,
    -- 使用窗口函数计算排名，按场次分组(PARTITION)，按总分降序
    RANK() OVER (
        PARTITION BY t.session_id 
        ORDER BY (t.balance + IFNULL(SUM(i.current_value), 0)) DESC, t.balance DESC
    ) as ranking,
    t.team_name,
    t.balance as remaining_balance,
    -- 拼接该组拥有的藏品代码，若无则显示'无'
    IFNULL(GROUP_CONCAT(i.item_code ORDER BY i.item_code SEPARATOR ','), '无') as items_owned,
    -- 计算藏品总价值，若无藏品则为0
    IFNULL(SUM(i.current_value), 0) as items_total_value,
    -- 计算总成绩 = 余额 + 藏品价值
    (t.balance + IFNULL(SUM(i.current_value), 0)) as total_score
FROM teams t
LEFT JOIN items i ON t.team_id = i.owner_team_id
GROUP BY t.session_id, t.team_id;

-- ==========================================

    remaining_balance as '剩余资金',
    items_owned as '获得藏品',
    items_total_value as '藏品总价值',
    total_score as '总成绩'
FROM view_game_results

ORDER BY ranking ASC;
