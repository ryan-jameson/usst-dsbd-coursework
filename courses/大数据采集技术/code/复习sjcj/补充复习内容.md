## 第1章 大数据概述

本章只保留会支撑后续章节的概念。1.5、1.6按你的判断降为低优先级；考试主线是定义、5V+1C、处理链、关键/支撑技术和四种科研范式。

### 1.1 三种大数据定义：原句、侧重点和共同核心

> **先纠正名称：** 用户口述的“维科”对应课件中的“维基百科”。课件第13页列出的三方是：维基百科、高德纳（Gartner）和麦肯锡全球研究所。

| 来源 | 课件定义（保持原意） | 答题时抓住的关键词 |
| --- | --- | --- |
| 维基百科 | 无法在可承受时间范围内，用常规软件捕捉、管理和处理的数据集合。 | 时间可承受范围；常规软件能力不足 |
| 高德纳 Gartner | 需要新的处理模式，才能具有更强决策力、洞察发现力和流程优化能力，以适应海量、高增长率和多样化的信息资产。 | 新处理模式；决策、洞察、流程优化；海量/高速增长/多样 |
| 麦肯锡全球研究所 | 规模大到在获取、存储、管理和分析方面，大大超出传统数据库软件工具能力范围的数据集合。 | 规模阈值；全流程超出传统数据库工具能力 |

三种说法并不矛盾。维基百科从“能否在合理时间处理”划界；高德纳强调“为什么必须换处理模式以及换了之后产生什么价值”；麦肯锡从“传统数据库工具能力边界”划界。共同核心是：数据的规模、速度和多样性超过传统工具的有效处理能力，因此需要新的分布式存储、计算和分析方法。

**5V+1C记忆链**

- Volume：容量大
- Variety：来源、类型、表示多样
- Value：总价值大，但单位数据价值密度低
- Velocity：产生快、处理快、时效要求高
- Veracity：结果要准确、可信
- Complexity：组织、处理和分析难度高

> **简答题模板：** 大数据不是“很多数据”的同义词。先写能力边界定义，再写需要新的处理模式，最后列5V+1C；若问与大规模数据的区别，再补“是否存在结构性和关联性、能否产生新价值”。

*资料定位：来源：第1章PPT第13—15页；教材重点1-01。*

### 1.2 三层架构与五阶段处理链

| 层次 | 包含什么 | 解决什么问题 |
| --- | --- | --- |
| 基础资源层 | 计算、存储、网络、HDFS、NoSQL、数据资源管理 | 把海量异构数据放得下、算得动、可扩展 |
| 管理与分析层 | 元数据、主数据、数据仓库、挖掘、预测、智能决策 | 把散乱数据组织起来并转化为信息、知识和预测 |
| 应用层 | 共享与交易、开放平台、应用接口、可视化工具 | 将结果提供给具体行业和业务 |

元数据是“描述数据的数据”，说明数据从哪来、格式是什么、何时更新；主数据是多个子系统交换共享的核心实体数据；数据仓库是面向主题、集成、随时间变化、相对稳定并服务决策的数据集合。三者不是同义词。

**五阶段主线（教材口径）**

- 采集 → 预处理 → 存储与管理 → 分析与挖掘 → 可视化

采集解决“拿到数据”；预处理解决“让数据可用”；存储管理解决“可靠保存和高效访问”；分析挖掘解决“发现模式和知识”；可视化解决“让结果可理解、可决策”。应用层可接在可视化之后，但考试问教材五阶段时不要用“应用”替换“可视化”。

*资料定位：来源：第1章PPT第19—30页；教材重点1-02、1-03；笔记页22。*

### 1.3 关键技术与支撑技术：不只背名词，要会说明关系

“关键技术”直接位于大数据处理流程中，决定数据如何进入、保存、计算和呈现；“支撑技术”提供运行这些环节所需的资源、数据入口或智能能力。答题时建议写“定义—作用—典型技术—与下一环节的关系”。

| 类别 | 核心任务 | 典型内容 | 与前后环节的关系 |
| --- | --- | --- | --- |
| 采集与预处理 | 汇集多源数据并清洗、转换、集成、归约 | 日志、ETL、爬虫、传感器；清洗/规范化 | 输入是原始数据，输出是较完整、一致、可计算的数据 |
| 存储与管理 | 海量数据持久化、组织、索引、扩展和容错 | HDFS、HBase、NoSQL、NewSQL、MongoDB | 接收预处理结果，为分析提供吞吐或低延迟访问 |
| 分析与挖掘 | 从不完全、有噪声、模糊和随机数据中提取模式 | 关联、聚类、分类、预测、机器学习、深度学习 | 把数据转化为规律、模型和决策依据 |
| 可视化 | 把数据及关系直观呈现 | 标签云、历史流图、聚类图、空间信息流、热图 | 降低理解成本，帮助发现异常和支持沟通 |
| 安全与隐私 | 控制采集、存储、使用和共享风险 | 接入代理、令牌化、加密、身份与访问管理 | 横跨全部流程，不是最后一步才做 |

| 支撑技术 | 为什么能支撑大数据 | 与关键技术的连接点 |
| --- | --- | --- |
| 云计算 | 通过互联网按需提供共享软硬件资源 | 弹性提供计算、存储和网络；支撑横向扩展 |
| 物联网 | 让传感设备与互联网连接，持续产生物理世界数据 | 是重要数据来源，也要求实时采集和流处理 |
| 机器学习 | 让程序从数据中学习规律并改善任务表现 | 支撑分类、聚类、预测、异常检测和智能决策 |

> **高频区分：** HDFS/HBase属于存储与管理；清洗、转换、集成、归约属于预处理；机器学习既可作为分析方法，也在课件中被列为支撑技术。题目按课件分类作答。

*资料定位：来源：第1章PPT第31—40页；教材重点1-02、1-03；笔记页22。*

### 1.4 第三范式与第四范式到底差在哪

| 范式 | 主要依据 | 典型过程 | 适合回答的问题 |
| --- | --- | --- | --- |
| 第一：实验科学 | 观察和可重复实验 | 提出问题→设计实验→测量→归纳 | 现象是否存在、条件改变会怎样 |
| 第二：理论科学 | 公理、定律、数学推导 | 建立理论→演绎推理→预测 | 机制和规律如何统一解释 |
| 第三：计算科学 | 已有理论模型+数值计算/仿真 | 把机制写成模型→设置参数→模拟→比较 | 理论方程难以解析求解时系统会怎样演化 |
| 第四：数据密集型科学 | 海量观测数据+统计/挖掘/机器学习 | 汇聚数据→预处理→发现模式→形成假设/预测 | 机制不完整或变量过多时，数据中出现了什么关联和模式 |

第三范式通常是“模型在前、数据在后”：研究者先根据物理或理论知识建立可计算模型，再用计算机仿真并由数据验证。第四范式常是“数据在前、模式在后”：先汇聚多源海量数据，通过统计和机器学习发现传统模型未预设的结构，再反过来提出或修正假设。

| 对比点 | 第三范式：计算科学 | 第四范式：数据密集型科学 |
| --- | --- | --- |
| 起点 | 理论/机制模型 | 大规模、多源、高维数据 |
| 核心手段 | 数值计算、仿真 | 数据挖掘、统计学习、机器学习 |
| 主要产出 | 给定模型和参数下的模拟结果 | 相关性、模式、预测模型和新假设 |
| 主要限制 | 模型假设错误会导致仿真偏差 | 数据偏差或伪相关会导致错误结论 |
| 关系 | 并非被第四范式淘汰 | 可为第三范式提供参数、验证和新假设 |

> **一句话答法：** 第三范式用计算机求解“人先建立的模型”；第四范式让算法从海量数据中发现“模型尚未明确表达的模式”。二者互补，不是新范式完全取代旧范式。

*资料定位：来源：第1章PPT第42页；教材重点第1章配套补充。*

## 第2章 大数据采集基础

本章是考试核心。新版重点补齐两种传统采集系统的组件与功能、三种采样方法、HDFS/HBase读写、分布式关系数据库局限，以及HBase低延迟访问的完整因果链。

### 2.1.1 数据采集链与两类传统数据采集系统

**传统数据采集主链**

- 物理量 → 传感器 → 信号调理 → 采样/保持 → A/D（量化+编码） → 计算机 → 显示/记录/控制

传感器把温度、压力、位移等物理量变成电信号；信号调理完成放大、滤波、隔离和线性化；多路开关在多个输入通道之间选择；采样/保持器在A/D转换期间保持电压稳定；A/D把模拟量变成数字码；计算机负责存储、处理、显示和控制。数字信号或开关信号可经接口直接进入计算机，不一定再经过A/D。

| 微型计算机系统组件 | 主要功能 |
| --- | --- |
| 传感器 | 把被测物理量转换成可处理的电信号 |
| 模拟多路开关 | 从多个模拟输入中选择当前采样通道 |
| 程控放大器/信号调理 | 放大、滤波、隔离，使信号匹配A/D输入范围 |
| 采样/保持器 | 在A/D量化编码期间保持采样瞬时值不变 |
| A/D转换器 | 完成量化和编码，输出数字信号 |
| 接口/计数器 | 接收数字量、开关量、脉冲量并与计算机交换数据 |
| 微型计算机 | 参数设置、主控、计算、存储、异常判断和输出 |
| 显示器/打印机/绘图仪 | 显示、记录和输出采集结果 |

微型计算机数据采集系统把采集和处理集中在一台计算机附近，结构简单、容易实现、成本低，适合通道数有限、距离较短的中小规模采集；集中点故障会影响整个系统，长距离布线也会增加噪声和维护成本。

| 主从式集散系统组件 | 主要功能 |
| --- | --- |
| 上位机/主机 | 统一配置、轮询或下发命令，汇总、显示、存储、分析各站数据 |
| 通信接口/网络 | 设置速率与协议，在上位机和各采集站之间传输命令、站号和数据 |
| 多个数据采集站/从机 | 就近连接传感器，独立完成本地采集、A/D、预处理、缓存和状态检测 |
| 现场传感器与调理电路 | 测量现场物理量并完成信号转换、滤波、放大和隔离 |

主从式集散系统把采集任务分散到多个现场站，把管理和汇总集中到上位机，因此适应能力强、可靠性高、实时响应好，对单台硬件要求不高。它比微机系统多出“通信接口+多个数据采集站”，也只有集散型系统必须具有通信程序。

> **组件功能题答法：** 先画或写数据流，再按组件解释功能。不要只写“微型系统简单、集散系统可靠”；题目问组成时必须出现传感器、调理、采样保持、A/D、计算机/上位机、接口与采集站。

*资料定位：来源：第2章PPT第4—8页；教材印刷页10—14；笔记页1—4、24（文件193259）。*

### 2.1.2 系统软件与开环/闭环

| 软件模块 | 功能 |
| --- | --- |
| 模拟信号采集处理 | 配置通道、量程、采样频率，完成滤波和标度变换 |
| 数字/脉冲/开关信号处理 | 读取状态、计数、测频，识别开关变化 |
| 运行参数设置 | 设置通道、频率、量程、阈值、采集时长 |
| 系统管理（主控） | 组织各模块运行，管理数据文件、显示和输出 |
| 通信程序 | 集散系统中设置波特率、发送站号/命令、接收并判断返回站号及数据 |

开环系统只采集和记录，采集结果不反向影响被测对象；闭环系统把结果反馈给控制器，控制器再调节执行机构。评价系统先看精度，再看处理速度：应在保证所需精度的前提下尽量提高采样和处理速度。

*资料定位：来源：第2章PPT第4、8页；教材印刷页12—14。*

### 2.1.3 采样、量化、编码与三种采样技术

**采样定理**

- fs ≥ 2 fmax
- 等价地：Ts ≤ 1 / (2 fmax)
- 其中fs为采样频率，Ts为采样周期，fmax为信号最高频率。

采样只让时间离散，幅值仍可连续；量化用最接近的离散等级代替采样幅值，使幅值离散；编码把量化值写成二进制码。A/D转换器负责量化和编码，题目不要把A/D写成只完成采样。

| 采样方法 | 工作方式 | 存储/信息代价 | 适用情形 |
| --- | --- | --- | --- |
| 常规采样 | 以固定fs连续采样，且fs满足采样定理 | 数据最完整，存储容量最大 | 频率相对稳定、需要完整波形 |
| 间歇采样 | 采一段、停一段；间歇时间段相等 | 主动丢弃部分信息；间歇比α越大，存储越少 | 允许牺牲时间连续性换取容量 |
| 变频采样 | 采样频率随信号频率或变化速度调整 | 通常略小于常规采样，信息损失小于间歇采样 | 信号频率随时间明显变化 |

间歇采样笔记中定义：若采样时段为tsi、间歇时段为tqi，则间歇比α=tqi/tsi；占用比例ε=α/(1+α)。α增大表示停采更久、信息丢失增多、存储空间减小。

> **小计算：** 若最高频率fmax=4 kHz，则理论最低采样频率fs=8 kHz；对应最大采样周期Ts=1/8000 s=0.125 ms。题目问“最低”按2倍取值。

*资料定位：来源：第2章PPT第9—17页；教材重点2-02、2-03；笔记页23（文件193254）。*

### 2.2 大数据采集：目的、来源、挑战与方法

大数据采集将现实世界中的多源数据通过技术手段集中、整合并进行简单处理，保存到大数据存储系统，作为后续分析和挖掘的原料。其三个要求是全面性、多维性和高效性：样本覆盖要足、属性维度要够、采集处理要及时且有针对性。

| 维度 | 传统数据采集 | 大数据采集 |
| --- | --- | --- |
| 数据源 | 较单一、量较少，常是传感器模拟信号 | 政府、企业、物联网、互联网等多源海量数据 |
| 类型 | 结构较单一 | 结构化、半结构化、非结构化并存 |
| 存储 | 关系数据库或并行仓库 | 分布式数据库、分布式文件系统 |
| 处理 | 常集中离线处理 | 低时效用批处理，高时效用流处理 |

- 五个挑战：数据分布；数据不稳定；无结构与冗余；错误或无效；结构复杂。
- 日志采集：读取系统自动产生、格式相对固定的操作或运行记录。
- ETL：Extract抽取→Transform清洗转换→Load加载；抽取可全量或增量。
- 网络爬虫：从种子URL按策略循环下载、解析、去重和扩展链接。

*资料定位：来源：第2章PPT第18—31页；教材重点2-04、2-05；笔记页22。*

### 2.3 HDFS：结构、适用边界、读流程与写流程

| 组件 | 保存什么/做什么 |
| --- | --- |
| NameNode | 维护目录树、权限、文件到Block的映射、Block到DataNode的位置；不传输实际文件数据 |
| DataNode | 保存Block，响应客户端读写，定期向NameNode发送心跳和块报告 |
| Block | 大文件切分后的存储单位，通常有多个副本分散在不同DataNode |
| Secondary NameNode | 周期性合并fsimage与edits形成检查点；不是热备NameNode |

HDFS针对超大文件、流式/批量访问和普通商用硬件设计。它追求高吞吐而非低延迟，所以不适合大量小文件、频繁随机修改、并发随机写和毫秒级随机查询。

**HDFS读流程**

1. 客户端把文件路径交给NameNode。
2. NameNode检查文件和权限，返回各Block及其副本所在DataNode列表，通常按距离排序。
3. 客户端直接与较近的DataNode建立socket连接，流式读取Block；NameNode不经过数据流。
4. 一个Block读完后继续读取下一个Block；若DataNode故障，切换到该Block的其他副本。

**HDFS写流程**

1. 客户端请求创建文件，NameNode检查路径、权限和同名文件。
2. 客户端把数据切成packet；NameNode为Block选择多个DataNode，形成复制pipeline。
3. 客户端发给第一个DataNode，第一个边写边转给第二个，依次复制。
4. 确认从pipeline末端逐级返回；Block写满后请求下一组DataNode。
5. 全部写完后客户端close，NameNode完成元数据提交。

> **可靠性因果链：** 副本解决节点故障；心跳发现DataNode失联；块报告让NameNode掌握副本状态；校验和发现数据损坏；再复制恢复副本数。

*资料定位：来源：第2章PPT第36—43页；教材重点2-06—2-08；笔记页5—6、21（文件193246）。*

### 2.4.1 分布式关系数据库为什么难适应大数据

| 局限 | 具体含义 | HBase方向 |
| --- | --- | --- |
| 规模效应压力 | 关系数据库更擅长纵向扩展，但单机CPU、内存和磁盘存在上限；大数据需要加节点横向扩展 | Region分区，增加RegionServer实现横向扩展 |
| 类型多样、价值密度低 | 关系模式要求预定义结构，海量稀疏、半结构化数据会带来模式和存储压力 | 列族、稀疏存储，空列不占空间，值统一为字节 |
| 设计理念冲突 | 关系数据库擅长事务记录和事后汇总；课件把大数据目标概括为事前预测 | 面向海量记录的快速随机读写，为分析系统提供数据 |

这里不是说关系数据库“不能分布式”，而是说传统关系模型中的复杂关系、强一致事务、固定模式和横向分片协调，在海量异构数据上成本更高。HBase用较简单的数据模型和访问方式换取规模与吞吐。

*资料定位：来源：第2章PPT第44页。*

### 2.4.2 HBase与关系数据库：按考点完整对比

| 比较项 | 关系数据库 | HBase |
| --- | --- | --- |
| 模型/类型 | 关系模型，字段有明确类型 | 稀疏、多维、排序映射；值统一视为字节 |
| 模式 | 表结构通常固定，列预先定义 | 列族预先定义，列限定符可动态增加 |
| 操作 | SQL、连接、拆分、复杂多表关系、事务 | 以行键为中心的Put/Get/Scan，不擅长复杂Join |
| 存储 | 典型按行存储 | 按列族组织，不同列族对应不同Store/HFile |
| 索引 | 可按不同查询建立多个索引 | 核心索引是RowKey；设计RowKey决定访问性能 |
| 更新/版本 | 更新覆盖旧值，通常只看当前值 | 时间戳标识版本，可保留多个历史版本 |
| 扩展 | 横向扩展和跨节点事务协调更难 | Region自动切分，增加节点横向热扩展 |
| 典型用途 | 结构化业务、事务、复杂查询 | 海量、稀疏、半/非结构化数据的随机读写 |

HBase的单元格由RowKey、Column Family、Column Qualifier、Timestamp共同定位；Region是HMaster分配管理的单位；一个Region按列族分为多个Store；每个Store包含一个MemStore和若干StoreFile（HFile）；HFile最终存于HDFS。

*资料定位：来源：第2章PPT第45—60页；教材重点2-09—2-11。*

### 2.4.3 HBase为什么能低延迟访问：必须写出完整读路径

**课程口径的HBase读路径**

1. Client先根据缓存或元数据定位RowKey所在Region及对应RegionServer。
2. RegionServer在内存层查找：MemStore包含尚未flush的新写入；BlockCache保存近期从HFile读入的数据块。读取时需要把可见版本合并判断。
3. 若内存未命中，再通过HDFS读取StoreFile/HFile中的数据块。
4. HFile副本若位于本机DataNode，本地/短路读取更快；否则通过网络到其他DataNode读取。
5. 从HFile读出的Block放入BlockCache，下一次相同或邻近数据可能直接在内存命中。

低延迟不是因为HDFS本身擅长随机读，而是HBase在HDFS之上增加了RowKey有序定位、Region划分、内存写缓存MemStore和读缓存BlockCache。热点数据命中缓存时可避开磁盘与网络；未命中时才回落到HFile。

> **严格表述：** MemStore和HFile中可能同时存在同一行的不同版本，实际读取会按时间戳、删除标记和可见性合并结果。因此“先内存、后HFile”是考试用的分层路径，不等于只要MemStore命中就永远无需检查其他文件。

*资料定位：来源：笔记页20（文件193242）及用户给定课程口径；PPT第59页。*

### 2.4.4 HBase写流程、HDFS与HBase读写对照

**HBase写流程**

1. Client定位目标RegionServer并发送Put。
2. RegionServer先把操作追加到WAL/HLog，保证故障后可恢复。
3. 再写入对应列族Store的MemStore；达到持久化条件后向Client确认。
4. MemStore达到阈值后flush为HFile/StoreFile写入HDFS。
5. 后台Compaction合并小HFile、清理过期版本/删除标记；Region过大时Split。

| 比较点 | HDFS | HBase |
| --- | --- | --- |
| 抽象 | 文件和Block | 表、RowKey、列族、Cell和Region |
| 读 | 先问NameNode位置，再按Block顺序从DataNode流式读 | 先定位RegionServer，再查MemStore/BlockCache，未命中读HFile |
| 写 | 文件按Block写入DataNode复制pipeline | WAL→MemStore→flush HFile→HDFS，再Compaction |
| 擅长 | 大文件顺序读写、批处理、高吞吐 | 海量记录的低延迟随机Get/Put和范围Scan |
| 不擅长 | 小文件、随机修改、低延迟查询 | 复杂多表Join、完整关系模型和通用SQL事务 |
| 关系 | 提供可靠分布式文件存储 | 建立在HDFS之上，提供结构化定位、缓存和随机读写 |

> **最容易混淆：** HDFS是底层文件系统，HBase是上层数据库。HBase不会取代HDFS；它把数据以HFile存到HDFS，并用Region/RowKey/MemStore/BlockCache把“文件块”变成“可随机访问的表记录”。

*资料定位：来源：教材重点2-07、2-11；笔记页20—21；用户补充说明。*

### 2.5 Hive：仓库抽象，不是低延迟事务数据库

Hive建立在Hadoop之上，把结构化文件映射为表，用户用HQL查询，Driver完成解析、编译、优化和执行计划，再交由底层计算框架处理HDFS/HBase中的大规模数据。元数据通常存MySQL/Derby等关系数据库，业务数据仍在HDFS。它适合大规模离线分析和类SQL使用体验；查询常需启动分布式任务，不适合毫秒级事务查询。

| 层/组件 | 作用 |
| --- | --- |
| 用户接口 | CLI、JDBC/ODBC等提交HQL |
| Metastore | 保存库、表、列、分区、文件位置等元数据 |
| Driver | 解释、编译、优化、生成计划并协调执行 |
| Hadoop底层 | HDFS存数据，MapReduce等框架执行任务 |

*资料定位：来源：第2章PPT第64—71页；教材重点2-12、2-13。*

## 第3章 系统日志数据采集

本章在原有Flume、Scribe基础上补全Chukwa和Kafka，并给出组件、数据流、可靠性和实时性的横向比较。

### 3.1 日志采集的对象、系统链与用途

| 日志类型 | 主要记录 | 典型用途 |
| --- | --- | --- |
| 用户行为日志 | 登录退出、访问页面、点击和使用程序 | 画像、体验改进、推荐 |
| 业务变更日志 | 谁在何时把什么对象从A改成B | 审计、追责、业务分析 |
| 系统运行日志 | 服务器、网络、中间件和应用状态 | 告警、运维、故障定位 |

**通用链**

- 日志源 → Agent/采集器 → 缓冲/消息通道 → Collector/Broker → HDFS/HBase等存储 → 查询分析/告警

采集系统的核心矛盾是：生产端持续写、下游处理速度波动。解决方式是分布式Agent、缓冲队列、批量发送、重试、副本或故障转储。

*资料定位：来源：第3章PPT第2—11页；笔记页7—8。*

### 3.2 Flume：Source—Channel—Sink与事务可靠性

| 组件 | 职责 | 考试易错点 |
| --- | --- | --- |
| Source | 接收日志，封装为Event并写入Channel | 不直接把数据写HDFS |
| Channel | 连接Source与Sink的缓冲区 | Memory快但故障可能丢；File较慢但可持久化 |
| Sink | 从Channel取Event并写入存储或下一个Agent | 成功后才从Channel提交删除 |
| Agent | 一个JVM中的最小独立运行单元 | 一个Agent可含多个Source/Channel/Sink |

Source到Channel和Channel到Sink分别由事务保护：写Channel失败会回滚；Sink发送失败不会把Event永久移出Channel，因此可以重试。多级Agent支持fan-in汇聚、fan-out复制和负载均衡。

*资料定位：来源：第3章PPT第12—22页；教材重点3-01、3-02。*

### 3.3 Chukwa：Adaptor、Agent、Collector和MapReduce后处理

| 组件/作业 | 功能 |
| --- | --- |
| Adaptor | 针对一种数据类型采集，如命令行输出、系统日志或应用日志；可定时轮询或事件驱动 |
| Agent | 运行多个Adaptor并发送数据；watchdog可重启终止的采集进程 |
| Collector | 接收多个Agent数据，先合并再写HDFS，避免大量小文件 |
| Demux | MapReduce作业：分类、排序、去重 |
| Archive | MapReduce作业：合并同类型数据文件 |

负载均衡：Agent可从Collector列表中随机选择目的端，避免单个Collector过载。容错：关键数据可在多台机器部署相同Agent形成冗余采集。后处理结果可进入MySQL或HBase用于展示。

> **局限：** Chukwa依赖MapReduce做离线后处理，延迟较高，不适合实时性要求强的场景；生态发展放缓后，常被Flume、Kafka等替代。

*资料定位：来源：笔记补充《第三章.pdf》第2页；笔记页15（文件193221）。*

### 3.4 Scribe：Store树与故障转储

Scribe是Facebook开源的分布式日志收集系统。数据源用Thrift Client发送“category + message”，Scribe按category路由到不同Store。中央存储故障时，可由Buffer Store转存本地/辅助Store，恢复后再回灌。

| Store | 作用 |
| --- | --- |
| File | 写本地文件、NFS或HDFS格式 |
| Network | 批量转发到其他Scribe服务器 |
| Buffer | 主Store故障时写辅助Store，恢复后重传 |
| Null | 丢弃不需要或未配置类别的数据 |
| Bucket | 按hash把消息分散到多个子Store |
| Multi | 将消息同时复制到多个子Store |

*资料定位：来源：第3章PPT第23—33页；教材重点3-03。*

### 3.5 Kafka：Producer、Broker、Topic/Partition和Consumer Group

Kafka是分布式发布—订阅消息系统，面向大量实时数据，核心特征是高吞吐、可扩展、分区、复制和高并发。Producer推送消息到Broker；Consumer主动从Broker拉取。

| 概念 | 含义 |
| --- | --- |
| Topic | 消息的逻辑分类名 |
| Partition | Topic的并行存储与处理单元；分区内部消息有序 |
| Broker | 组成Kafka集群并保存分区副本；一个Broker管理多个Partition |
| Producer | 决定消息进入哪个Partition，支持batch、异步和并行发送 |
| Consumer Group | 以组为单位消费Topic；组内分摊分区，组间各自得到一份数据 |

组内表现为队列：一个分区在同一组内只分配给一个消费者，从而并行且不重复；组间表现为发布—订阅：不同组可以各自完整消费同一Topic。Kafka通过分区提高并行度，通过副本提高可用性，通过批量与顺序追加写提高吞吐。

> **顺序范围：** Kafka只保证同一Partition内的顺序，不保证整个Topic跨Partition的全局顺序。若业务要求同一对象有序，应使用相同Key把相关消息送入同一Partition。

*资料定位：来源：笔记补充《第三章.pdf》第3—4页；笔记页16（文件193225）。*

### 3.6 四种采集系统横向辨析

| 系统 | 核心结构 | 传输/消费特征 | 强项 | 主要局限 |
| --- | --- | --- | --- | --- |
| Flume | Source—Channel—Sink Agent | Push/Push；事务Channel | 日志汇聚、HDFS落地、链式拓扑、可靠性 | 主要面向采集管道，不是通用消息平台 |
| Scribe | Thrift Client/Server + Store树 | Push/Push；Buffer故障转储 | 按category路由、Store组合灵活 | 容错和负载均衡常需配置/实现 |
| Chukwa | Adaptor/Agent→Collector→HDFS→MR | Push/Push；批后处理 | 监控Hadoop大集群、合并小文件 | 依赖MapReduce，延迟高 |
| Kafka | Producer→Broker/Partition→Consumer Group | Push/Pull；消息保留与回放 | 高吞吐实时消息、多消费者组、扩展性 | 需要设计分区、消费位点和副本 |

> **选型题：** 直接收集日志并落HDFS：Flume；需要多消费者、实时缓冲和可回放：Kafka；考早期Facebook日志：Scribe；考Hadoop监控且有Collector+MapReduce后处理：Chukwa。

*资料定位：来源：笔记补充《第三章.pdf》第4页；笔记页17（文件193229）；表中采用课程对比口径。*

## 第5章 互联网数据采集

本章先分清“爬虫算法的两类分析依据”，再理解七种URL调度策略。局部PageRank、OPIC、反向链接和相似度策略都不能只写优点，还要写广告/作弊操纵风险。

### 5.1.1 网络爬虫循环与两类网页分析算法

网络爬虫是按规则定向或不定向抓取网页数据的程序或脚本，通常包含采集、处理和存储三部分。基本循环是：种子URL入队→取URL→下载→解析内容与链接→去重/过滤→新URL排序入队→达到停止条件。

| 算法类别 | 依据 | 典型信号/方法 | 主要风险 |
| --- | --- | --- | --- |
| 基于网络拓扑 | 页面之间的超链接图 | 深度/广度、PageRank、局部PageRank、OPIC、反向链接数、大站优先 | 链接农场、广告链接和作弊链接可人为抬高重要性 |
| 基于网页内容 | 正文、标题、锚文本、关键词和语义 | 关键词匹配、向量/余弦相似度、分类器、最佳优先 | 关键词堆砌、广告文本、模板噪声可造成伪相关 |

拓扑算法回答“网页在链接网络中是否重要”；内容算法回答“网页与目标主题是否相似”。主题爬虫通常把二者融合：先用链接扩展候选，再用内容相关度过滤或重排。

*资料定位：来源：第5章PPT第4—8页；教材重点5-01、5-02。*

### 5.1.2 七种抓取策略：排序依据、优点与陷阱

| 策略 | URL队列如何排序 | 优点 | 局限/作弊点 |
| --- | --- | --- | --- |
| 深度优先 | 沿一个分支不断向下，走不通再回溯 | 适合站内和垂直深挖 | 深层无关页面会浪费资源 |
| 广度优先 | 逐层遍历候选URL | 覆盖均匀；靠近种子通常更相关 | 盲目搜索，规模大时效率低 |
| 局部PageRank | 对已下载页+候选页组成的局部图计算PR后排序 | 利用链接结构估计重要性 | 广告/作弊链接使PR虚高，数据可能无效 |
| OPIC | 按页面累计cash排序；抓取后把cash分给出链 | 无需反复迭代，适合在线实时计算 | 仍依赖链接投票，链接农场/广告网络可操纵cash |
| 大站优先 | 按待抓页面数量归类，页面多的网站优先 | 大型站点通常资源多、内容较稳定 | 小而高质量的垂直站被延后；站点规模也可伪装 |
| 反向链接数 | 被其他网页指向越多越先抓 | 简单表示受推荐程度 | 链接购买、互链和广告链接可刷数量 |
| 最佳优先 | 按候选URL与目标页面/主题的预测相似度排序 | 只访问预测有用页面，节省抓取 | 局部最优会漏掉需经暂时低相关页面才能到达的内容 |

OPIC的直觉：所有页面初始现金相同；页面P被下载后，把P当前现金平均或按规则分给P解析出的出链，P的现金清空或记入历史量；候选URL按累积现金排序。它比PageRank少了全图迭代，但并没有自动解决作弊链接。

> **你点名的共同问题：** 局部PageRank、OPIC、反向链接数属于“链接投票/重要性”思想，主题相似度和最佳优先属于“内容相关性”思想。前者会被广告、互链、链接农场操纵；后者会被关键词堆砌和广告文本欺骗。稳妥做法是可信域名、广告/模板过滤、重复检测，并融合链接分与内容分。

*资料定位：来源：第5章PPT第8—16页；教材重点5-02；笔记页19含局部PR示意。*

### 5.2 robots、更新策略与爬虫类型

- robots.txt位于站点根目录，声明User-agent、Allow、Disallow等规则；它是行业约定，不是技术访问控制，也不等于法律授权。
- 更新策略可按用户体验优先更新高排名网页，或根据历史变化规律预测下次更新时间。
- 通用爬虫追求覆盖广；聚焦爬虫只保留主题相关页面；增量爬虫更新已有库；深层网络爬虫处理表单后数据；分布式爬虫多节点并行。

| 类型 | 目标 | 关键机制 |
| --- | --- | --- |
| 通用爬虫 | 尽可能覆盖公开网页 | 大规模URL队列、去重、调度 |
| 聚焦爬虫 | 获取某主题高相关页面 | 内容判定、链接预测、主题过滤 |
| 增量爬虫 | 只抓新增或发生变化的页面 | 更新时间预测、指纹/版本比较 |
| 深层网络爬虫 | 获取表单查询后才出现的数据 | 表单理解、参数组合、会话维护 |

## 第6章 数据预处理技术

本章计算多。新版重点把混合类型相异度拆成“每个属性先算、缺失/不适用再屏蔽、最后按有效属性平均”，并补充清洗、集成、规范化、PCA和ChiMerge的计算抓手。

### 6.1 属性类型、中心趋势与离散程度

| 属性 | 可做的比较 | 例子 |
| --- | --- | --- |
| 标称 | 只判断相同/不同，无顺序 | 颜色、专业、地区 |
| 二元 | 只有0/1；分对称与非对称 | 性别可作对称；是否患病常作非对称 |
| 序数 | 有顺序但相邻差值无固定意义 | 优秀/好/一般 |
| 数值 | 差值和算术运算有意义 | 年龄、温度、收入 |

**常用统计量**

- 均值：x̄ = Σxi / n
- 总体方差：σ² = Σ(xi-x̄)² / n
- 总体标准差：σ = √σ²
- 极差：R = max(x)-min(x)
- 中列数：midrange = [max(x)+min(x)]/2

均值使用全部数据但受极端值影响；中位数抗异常值；众数适用于标称属性；截尾均值先删两端一定比例再求均值。分位数计算按课程规则确定位置，位置非整数时按相邻观测值处理。

*资料定位：来源：第6章PPT第2—37页；教材重点6-01、6-02；笔记页17。*

### 6.2.1 单一属性的相异度：先分类型再套公式

| 属性类型 | 相异度dij(f) | 关键说明 |
| --- | --- | --- |
| 标称 | 相同为0，不同为1 | 也可用不匹配属性数/属性总数 |
| 对称二元 | 相同为0，不同为1 | 0和1同等重要 |
| 非对称二元 | 共同为0通常不计；一个1一个0计1 | 常用Jaccard，阳性1更重要 |
| 数值 | \|xif-xjf\| / (maxf-minf) | 先按极差归一化，避免量纲支配 |
| 序数 | 先转zif=(rif-1)/(Mf-1)，再按数值距离 | 课程PPT排序方向可反，但要前后一致 |

**二元属性计数**

- q：两对象都为1的属性数
- r：对象i为1、j为0
- s：对象i为0、j为1
- t：两对象都为0
- 对称距离 d=(r+s)/(q+r+s+t)
- 非对称Jaccard距离 d=(r+s)/(q+r+s)

> **非对称为什么忽略0-0：** 在“患病/阳性/购买”等属性中，1表示稀少且重要的存在；两个对象都没有该特征（0-0）不能说明它们很相似，所以从分母中排除。

*资料定位：来源：第6章PPT第38—55页；教材重点6-03、6-04；笔记页18。*

### 6.2.2 混合类型属性相异度：公式、δ开关与完整例题

**混合属性总公式**

- d(i,j) = [Σf δij(f) · dij(f)] / [Σf δij(f)]
- δij(f)=1：属性f对本次比较有效；δij(f)=0：缺失或按规则不计。

算法的本质是：每个属性先按自己的类型变成0—1之间的相异度，再只对“有效属性”求平均。δ是开关，不是距离。出现缺失值时设δ=0；非对称二元若两对象都为0，也可设δ=0，因为共同缺失阳性信息不构成相似证据。

| 对象 | 颜色（标称） | 患病（非对称二元） | 年龄（数值） | 等级（序数） |
| --- | --- | --- | --- | --- |
| A | 红 | 1 | 20 | 高 |
| B | 蓝 | 0 | 30 | 中 |

**例题计算（年龄范围10—50；等级低<中<高）**

1. 颜色不同：d1=1，δ1=1。
2. 患病1与0不同：d2=1，δ2=1。
3. 年龄：d3=|20-30|/(50-10)=10/40=0.25，δ3=1。
4. 序数：低/中/高对应r=1/2/3，z=(r-1)/(3-1)；A为1，B为0.5，所以d4=0.5，δ4=1。
5. 总距离d(A,B)=(1+1+0.25+0.5)/4=0.6875。

> **缺失值变化：** 若B的年龄缺失，则δ3=0，分子和分母都删除年龄项：d=(1+1+0.5)/3=0.8333。不能把缺失值的距离直接当0，否则会把“不知道”误当“完全相同”。

课堂笔记PPT例子中P1为标称、P2为序数、P3为数值：先分别构造三个距离矩阵，再逐元素平均。若某一属性对某对对象无效，平均时分母必须减小。

*资料定位：来源：第6章PPT第56—58页；笔记页17（文件193229）和笔记页18（文件193234）。*

### 6.3 数据质量、清洗与分箱

| 质量维度 | 问题表现 |
| --- | --- |
| 准确性 | 数值错误、录入错误、OCR错误 |
| 完整性 | 字段或记录缺失 |
| 一致性 | 同一实体在不同源中冲突 |
| 时效性 | 数据过期或更新不及时 |
| 可信性 | 来源不可靠或采集过程不透明 |
| 可解释性 | 字段含义、单位、编码不清 |

- 缺失值：删除元组；人工填充；全局常量；均值/中位数/众数；按类别统计量；预测模型。
- 噪声：分箱、回归、聚类、异常检测。
- 不一致：统一单位、编码、命名、日期格式并设置约束。

等深分箱先排序后让每箱记录数接近；等宽分箱让区间宽度相等。箱均值把箱内值替换为均值；箱中位数替换为中位数；箱边界把每个值替换为最近的边界。

### 6.4 数据集成：冗余、相关系数、协方差与卡方

**数值属性关系**

- Pearson相关系数 r = Σ(xi-x̄)(yi-ȳ) / [n·σx·σy]（按课程总体口径）
- 协方差 cov(X,Y)=Σ(xi-x̄)(yi-ȳ)/n
- r接近1：强正相关；接近-1：强负相关；接近0：无线性相关。

相关系数是标准化协方差，所以无量纲且范围[-1,1]；协方差的正负表示方向，但大小受量纲影响。相关不等于因果。名义变量之间可用卡方检验比较观察频数与期望频数的差异。

**卡方统计量**

- χ² = Σ (O-E)² / E
- O为观察频数，E为独立假设下的期望频数；自由度df=(行数-1)(列数-1)。

> **卡方表来源：** 笔记补充《第三章.pdf》第1页虽然文件名属于第三章，但内容是卡方临界值表，应在本节使用。计算χ²和自由度后查表判断是否拒绝独立假设。

*资料定位：来源：第6章PPT数据集成部分；教材重点6-08；笔记补充《第三章.pdf》第1页、笔记页18。*

### 6.5 数据变换与三种规范化

| 方法 | 公式/做法 | 特点 |
| --- | --- | --- |
| 最小—最大 | v'=(v-minA)/(maxA-minA)×(new_max-new_min)+new_min | 保留相对位置；对新极值敏感 |
| Z-score | v'=(v-μ)/σ | 转为均值0、标准差1；不要求原范围已知 |
| 小数定标 | v'=v/10^j | 选最小j使max\|v'\|<1 |

- 平滑：降低噪声；聚集：汇总明细；泛化：用高层概念替代低层值。
- 属性构造：由已有属性生成新属性；离散化：连续值转区间；规范化：统一尺度。

> **易错：** 最小—最大规范化分母是原极差；Z-score分母是标准差；小数定标的j由最大绝对值位数决定。

### 6.6 数据归约、PCA、小波与ChiMerge

| 归约类别 | 方法 | 保留什么 |
| --- | --- | --- |
| 维归约 | 属性子集选择、PCA、小波变换 | 用更少属性/分量保留主要信息 |
| 数量归约 | 抽样、聚类、回归、直方图 | 用较少对象或模型代表原数据 |
| 数据压缩 | 有损/无损编码 | 以更少空间表示数据 |

**PCA计算主线**

1. 对各属性中心化/标准化。
2. 计算协方差矩阵或相关矩阵。
3. 求特征值与特征向量。
4. 按特征值从大到小排序，选择累计贡献率达到阈值的前k个主成分。
5. 用选中的特征向量把原数据投影到低维空间。

**贡献率**

- 第i主成分贡献率 = λi / Σλj
- 累计贡献率 = Σ(i=1..k)λi / Σλj

小波变换把数据表示成不同尺度的近似系数和细节系数，可保留主要低频结构并压缩或去噪。ChiMerge先把连续属性的相邻值作为小区间，计算相邻区间类别分布的卡方值，优先合并差异最小（χ²最小）的相邻区间，直到达到阈值或目标区间数。

> **ChiMerge方向：** χ²小表示相邻区间类别分布相近，应优先合并；χ²大表示差异明显，应保留边界。
