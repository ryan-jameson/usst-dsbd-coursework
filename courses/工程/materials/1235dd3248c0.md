1  实习技术总结
1.1  AI时代的开发-来自软件开发公司的探索与实践
1.AI开发基本认识
目前主流大模型本质是基于概率的下一个词预测系统，通过训练学习文本概率关系，在推理时生成输出；经过OpenAI、DeepMind、NVIDIA共识，AGI时代（创造出像人类一样学习、思考、执行多种任务的系统）在3-5年内可能会到来，社会分层也会改变，底层为最广的AI使用者，其次是AI产品制造者最后是 基础模型开发者。
作为开发者，需要懂业务（商业模式）、懂AI（技术解法） 、懂编程（工程实现），在与AI交互时要"把AI当人看"，学习时当老师、工作中当助手、休闲时当朋友。
2.AI开发的主要内容
提示词工程（Prompt Engineering）是操作大模型的唯一接口，其中设计要素在于：角色定义 + 任务指示 + 上下文 + 示例 + 输入 + 输出，其中包含思维链引导推理、参考文本注入（通过分隔符标记知识片段）、任务拆解（复杂任务→原子化子任务）
Agent结合了Function Calling与MCP协议，其中Function Calling是模型主动调用函数的能力，MCP协议是跨模型协同的通用标准。

模型微调（Fine-tuning）：预训练模型的领域适应，关键工艺在于参数冻结，80%底层参数锁定；局部优化，20%参数梯度更新；数据要求，数千条高质量领域样本。

1.3  区块链技术的原理与应用
1.技术原理​​
核心架构在于分布式账本，多个节点共同维护数据副本（全节点/轻节点），实现去中心化存储；链式结构，区块按时间顺序链接，每个区块包含交易集合及前区块哈希值；密码学保障包括哈希函数，确保区块唯一性及非对称加密，实现数字签名与身份认证；共识机制包括公链，PoW/PoS等经济博弈机制及联盟链包括PBFT/Raft等高效算法，需授权节点参与
2.运行流程
1）提议区块：节点从交易池选交易 → 执行生成DAG → 广播  
2）共识投票：节点按链上机制对候选区块投票  
3）区块验证：全网节点验证交易合法性  
4）账本更新：验证通过后写入链，交易移出缓存  
3.安全特性
1）不可篡改：区块哈希链 + Merkle树结构，单点修改导致后续哈希失效
2）抗抵赖：数字签名绑定身份与交易
3）动态防御：P2P网络节点自由进出，恶意节点快速隔离

2 技术应用案例设计或设想
项目背景：
在生成式AI技术深度渗透日常工作的产业背景下，本项目的创意萌芽源自对AI应用痛点的双重观察：越来越多人开始使用AI平台进行一些日常工作的辅助，但是随着更多人使用与联网搜索功能的应用，网页中有很多未经辩证正确的数据被AI生成输出，导致AI输出不正确的内容有很多，且在与AI进行沟通时，用户也经常出现信息输入不完整导致AI输出内容并非用户想要得到的。技术层面，OpenAI等平台数据显示，未接入专业领域知识的通用大模型在文旅场景中的错误率高达37%，且因用户需求表述不完整导致的重复沟通率达68%；市场层面，上海市文旅局2023年调研显示，87%的游客期待获得建筑文化深度解读，以及行程规划、热点景点推荐等更多旅游时需要得到的信息。但现有导览系统仅能提供基础信息的单向输出。这种技术局限与市场需求的结构性矛盾，催生了"理宝"系统的研发构想。
“理宝”致力于打造一个基于 RAG（检索增强生成）和 LangGraph 的旅游热点建筑知识大模型的AI 推荐系统。我们紧贴上海市文旅局提出的“建筑可阅读”新概念，以 AI 技术赋能文旅体验，让游客深度了解旅游热点建筑背后的历史、文化和设计理念，以及根据知识库智能推荐，为用户完整介绍出游规划以及具体行程安排。平台通过对接上海市历史建筑数据库及实时文旅数据，结合多模态交互能力，可智能生成个性化旅游安排、建筑文化故事及特点解读，实现"建筑可阅读"的数字化升级。
项目核心优势体现在三方面：首先，依托RAG技术确保内容权威性，结合本地知识库与外部信息，为用户提供精准且深入的建筑文化介绍；其次，运用LangGraph构建动态知识图谱， 基于用户偏好和行程安排，智能推荐建筑景点、周边美食和交通方案，基于数据库支持历史对话记忆与总结。最后，加深交互式探索体验用户可以与 AI 助手进行多轮对话，探索建筑背后的故事，定制专属建筑旅行路线，增强游览沉浸感。
本项目不仅是一个技术平台，更是对“建筑可阅读”、AI赋能文旅理念的积极响应。我们旨在打造一个连接建筑、文化和游客的桥梁，让每一位用户都能感受到旅游文化的独特魅力，体验更富深度、更有温度的文化之旅。通过我们的平台，热点建筑将不再是冰冷的钢筋水泥，而是充满故事、值得探索的城市文化名片。
系统功能：
本系统综合使用了人工智能与现代化软件开发技术，实现高效、智能的旅游行程规划功能。在理论技术层面，系统采用了检索增强生成（Retrieval-Augmented Generation, RAG）技术、基于LangGraph认知推理，通过大语言模型生成与向量检索，有效提高生成内容的准确性与实用性。大语言模型采用的是通义千问（Qwen-plus），具备强大的语言理解与生成能力，适用于处理用户复杂的旅游规划需求。
开发技术方面，后端服务采用了FastAPI Web框架，这是一款高效、异步的Python Web框架，具备良好的性能表现与开发效率。数据存储方面，系统使用了Milvus向量数据库管理旅游知识库与用户偏好信息，支持高效的语义相似性检索；同时使用了MySQL数据库存储用户信息、历史行程数据以及任务状态，实现了状态的持久化与恢复功能。前端界面开发则基于React 18 + Ant Design 框架，通过企业级UI组件库构建了高交互性、响应迅速的用户界面，提供流畅的用户体验。在数据传输上，前后端采用 WebSocket 协议与后端 FastAPI 服务建立全双工通信通道，网页利用 React Context和useReducer管理全局会话状态，整体编程语言采用Python与JavaScript，兼顾开发效率与生态兼容性。
通过五大模块的有机协同，系统实现从“数据沉淀-智能分析-服务输出”的闭环运作：用户交互数据持续反哺知识图谱优化，形成“越用越懂用户”的良性进化机制。该架构设计为AI+文旅场景提供了可复用的功能模块化解决方案。

用户管理：提供基础账户服务（登录/注册），建立用户画像基础数据池，支持跨设备同步与多终端适配，为个性化推荐提供身份标识与偏好沉淀载体。
历史对话管理：查看历史对话以及历史行程总结，存储多轮对话上下文，归档用户历史行程方案及交互反馈，同时可以对历史行程进行更改，动态优化知识图谱。
行程管理：对话前可以创建新行程或选择历史行程，实现全流程数字化服务，基于建筑时空分布、用户偏好（停留时长/兴趣标签）的智能生成行程，结合实时用户对话数据动态优化，调整路线优先级。
系统分析：部署三重智能分析引擎；提取路径规划中的建筑风格、住宿需求、饮食需求、出行安排等聚类特征进行行程特征总结；通过对话行为分析构建用户画像标签体系；运用协同过滤算法实现跨用户群体的知识传播优化以更能直击用户偏好。
对话管理：创新异步处理机制，采用分级队列管理高并发请求；通过向量检索实现上下文精准召回，调用历史记忆。
本系统整体采用模块化设计架构，主要由RAG（Retrieval-Augmented Generation，检索增强生成）模块、数据库模块以及LangGraph工作流模块三部分组成。系统按照功能职责划分模块，各部分相互协作、层次分明，以保证整体结构具有良好的扩展性与可维护性。Agent作为核心调度中枢，负责接收用户输入的自然语言信息，理解意图后根据具体需求调用相应工具模块（如搜索引擎、行程生成器）或访问数据库获取知识，并最终生成个性化回复返回给用户。Agent的整个处理流程由LangGraph模块进行流程管理，该模块定义了对话路径、分支决策和执行顺序，确保了多步任务可以有逻辑地执行，支持更复杂的上下文理解与智能规划能力。
在信息获取与生成过程中，RAG模块扮演着至关重要的角色。通过集成的搜索工具（Search）和行程文本生成器（Generator），系统可以在需要时实时获取网络信息，并结合本地旅游知识库中的向量化语义数据进行召回，从而提升回复的准确性与时效性。为增强生成效果，系统还设计了提示词注入机制，将用户意图与场景相关数据动态融合进生成请求中，从而构造出更契合用户需求的回复内容。同时，系统使用Milvus构建向量数据库，管理本地知识和用户偏好信息；使用MySQL作为结构化数据存储，用于存放用户资料、历史对话记录等内容。这种异构数据库结构使得系统能够在长期交互中“记住”用户的兴趣与习惯，从而不断提升个性化推荐的效果。
总体来看，系统整体结构自上而下可分为三层：表示层（用户交互界面）、逻辑控制层（Agent与工作流模块）、数据支撑层（工具模块与数据库）。各层之间通过标准化接口连接，调用路径清晰，职责划分明确，既能支持快速原型开发，又适合未来功能迭代与模块扩展。系统中各个模块之间的调用关系也已通过结构图进行明晰化展示，为后续的开发、调试和部署提供了坚实的架构基础。

模块接口、系统间接口：
本系统采用模块化设计，系统内部各模块间通过统一的数据结构进行通信与信息交互，确保系统功能解耦、逻辑清晰。系统之间或模块之间的信息交换主要通过以下几种方式实现：共享内存数据结构（对象传递）、数据库共享（MySQL）、参数传递与方法调用、基于工具层的消息回调机制。以下分别对主要模块接口和数据格式进行说明：
1. Agent 与 State 模块接口
在用户发起新的行程规划请求或恢复历史任务时，Agent 会通过读取 MySQL 数据库中 itinerary 表的记录，构造并初始化 State 类的实例。此类对象在内存中以字典形式存在，作为上下文容器在整个 LangGraph 流程中传递。其核心字段包括用户信息、行程参数、喜好标签、历史对话等。State对象作为模块间（如Agent → RAGModule、Agent → Generator）的参数载体，在系统内部以共享内存对象的形式流动。
数据格式示例如下：
{
  "user_id": 10001,
  "user_name": "Alice",
  "itinerary_name": "夏季香港三日游",
  "destination": "香港",
  "departure": "广州",
  "start_date": "2025-07-10",
  "end_date": "2025-07-13",

2.Agent与RAGModule 模块接口
Agent 需要在生成推荐内容或行程前调用 RAGModule.search(query: str) 方法从本地知识库中检索相关内容。此接口以自然语言字符串作为查询参数，返回与语义最接近的文本内容列表。检索结果格式为：
[
  {"text": "推荐前往太平山顶，观赏香港夜景。", "doc_id": "guide_001"},
  {"text": "香港的中环拥有丰富的美食文化...", "doc_id": "guide_002"}
]
数据在模块之间通过方法调用与返回值传递完成，RAGModule 在内部基于向量数据库进行嵌入检索，并将文本块返回给调用者（Agent），供后续提示词注入或行程内容生成使用。
3. 系统与MySQL接口
系统通过 ORM（如 SQLAlchemy）或原生 SQL 查询从 MySQL 数据库中读取或写入数据。MySQL 数据库承担两个关键职责：存储用户的 itinerary 行程表：用于初始化与持久化 State；存储历史对话记录表与用户信息表：用于长期交互分析与偏好建模。数据交换格式符合 MySQL 数据表结构，字段与 State 中的数据结构保持一致。
4. 工具层接口（Search、Generator）
系统中调用Search和Generator工具模块时，Agent将构造标准格式的工具调用请求，如：
{
  "tool": "Search",
  "input": "7月香港有哪些必去景点？"
}
工具模块在处理完请求后返回JSON格式的响应，由Agent解析并存入State.messages以供后续调用。
数据结构：
本系统采用面向对象的程序设计方法，核心功能通过类结构组织，并结合数据库实现状态的持久化与恢复。在用户与系统进行交互的全过程中，系统主要依赖两个关键类结构：State类和 RAGModule类，分别承担对话上下文管理与知识检索存储的职责。为了支持长对话、多轮交互及跨会话恢复能力，系统还设计了基于MySQL数据库的行程信息查询机制，实现历史状态的初始化与任务进度的延续。
State 类是系统中用于管理用户当前行程规划任务上下文的核心数据结构，基于 Python 的 TypedDict 类型构建。其主要作用是在 Agent、User 与工具模块（如搜索工具和生成工具）之间传递信息，记录整个规划过程中的关键参数和执行状态。其包含的字段涵盖了用户基本身份信息（如 user_name、user_id）、当前规划任务的核心数据（如destination、departure、start_date、end_date、time、preferences 等），以及系统生成的行程内容（details）和状态标记（flag）。此外，messages 字段保存了多轮对话内容，支持上下文的连贯传递与动态插入，是 LangGraph 工作流执行过程中的重要判断依据。
在用户开始一次新的会话时，系统会首先根据其身份信息（user_id）与行程名（itinerary_name）查询 MySQL 数据库中 itinerary 表中的对应记录。若存在，则从中提取相关行程字段并初始化 State 实例，以复原此前的任务进度与用户偏好。这一机制使得系统具备“跨会话记忆”能力，即使用户中断或关闭会话，也能在后续继续其未完成的旅行规划任务，提升了用户体验的连续性与智能性。
RAGModule 是系统中用于管理本地旅游知识向量化信息的核心类，封装了与 Milvus 向量数据库的连接、写入与检索操作。系统在初始化阶段调用 RAGModule 中的构造方法，自动连接 Milvus 数据库，并检测目标集合（collection）是否存在，若不存在则创建新的集合，并为 embedding 字段建立向量检索索引。在后续运行中，系统通过该模块的方法 update_from_json() 将新增的旅游攻略文档以 JSON 格式加载进系统，经过文本清洗、分段、向量化处理后，批量插入向量数据库，实现知识库的动态扩展。
此外，RAGModule 提供了is_duplicate()方法用于文档去重判断，避免重复插入，提高数据管理效率。其最关键的功能是search()方法，通过接收用户查询文本，利用OpenAI向量嵌入模型（text-embedding-ada-002）将文本转换为高维向量，并在 Milvus 中执行语义相似度检索，从而召回与用户需求最相关的旅游信息文本块。这些内容随后会被注入到提示词模板中，参与行程生成器（Generator）的响应内容构建，是系统实现检索增强生成（RAG）能力的基础。

算法设计：
本系统的核心功能在于实现一个基于自然语言交互的个性化旅游规划智能体。其关键能力包括：用户意图识别、上下文记忆管理、动态调用外部搜索与本地知识生成内容，以及行程规划的自动化。整个功能依托于RAG、LangGraph工作流调度和高效的数据存储与检索机制共同实现。系统采用面向流程的控制逻辑，并集成了语义相似度搜索、提示词动态注入、函数调用链路优化等关键技术。
用户通过网页输入旅游需求信息后，系统首先将自然语言输入交由Agent模块解析，识别意图与上下文状态。Agent随后根据任务需求调用LangGraph工作流节点，依次判断是否需从外部网络搜索数据（如实时票价、景点开放信息）、或从本地知识库中召回相关内容。该召回过程通过Milvus向量数据库实现，基于语义相似度计算检索本地旅游数据与用户兴趣偏好（Agent记忆库），从而实现个性化推荐。
生成模块则采用提示词注入机制（Prompt Injection）将用户意图、召回知识、历史偏好融合成输入模板，交由生成器（使用qwen-plus大模型）产出多轮对话或结构化行程建议。此外，为了提升执行效率和避免冗余操作，系统在LangGraph节点中内嵌判断逻辑，对已有会话状态进行缓存管理，仅在必要时重新检索或调用生成器。历史对话记录与用户信息被存储在MySQL数据库中，部分常用数据调用也通过预定义存储过程完成，如“用户兴趣标签更新”、“城市偏好记录写入”等，以提升数据库写入效率并确保数据一致性。
系统的优化策略主要体现在以下几个方面：一是RAG模块通过召回+生成组合，避免了大模型直接生成导致的不准确与幻觉；二是提示词注入方式使模型生成更具上下文适应性；三是使用LangGraph的流程节点进行功能拆解，实现“可视化”、“可复用”的多步对话逻辑；四是通过Milvus支持向量级别的模糊召回，实现语义检索而非关键词匹配，提升推荐准确度与个性化能力。
在具体实现上，Agent规划用户旅游行程的大致流程如下：
首先，系统会根据用户输入信息提取是否已明确旅行目的地。如果用户未提供具体城市或村镇名称，Agent将调用网络搜索工具进行辅助检索，从搜索结果中提取满足用户意图的目的地候选，并附带简介与链接引导用户选择。随后，系统确认用户的出发地，若未给出则进行追问。接着，系统会逐步引导用户补充旅游需求，包括出发时间、行程天数、交通方式、预算、游玩偏好、同行人员及住宿类型等。这一阶段支持多轮对话与动态查询，通过Search工具实时为用户推荐相关酒店、活动、路线等内容。
当用户对初步行程安排表示确认后，Agent将综合用户所有需求，通过调用行程规划工具（Generator）生成详细的旅行计划，并将生成结果展示给用户确认。若用户提出修改意见，系统将自动调整参数、重调工具并重新生成优化方案，确保行程贴合用户期望。此流程高度模块化、可反复修正，是本系统实现“智能、交互、个性化”规划体验的核心设计之一。

数据基础设施层（database）：
利用Milvus向量数据库存储本地知识库；MySQL存储用户及上下文信息，管理结构化业务信息；src文件夹中则实现了封装操作，实现数据库连接管理、数据交换。
核心服务层（core service）：
前端AuthContext接受来自后端auth.py在/login发放的JWT令牌进行用户身份认证和用户管理；而/ws/itinerary则接收来自后端工作流处理过后的回复信息，后端则融合本地知识库及Agent记忆进行知识管理。
认知增强层（knowledge processing）：
通过graph.py设置LangGraph驱动的动态图谱编译器，将知识库构建成网络图谱，基于多跳推理引擎发起工作流，从而优化理宝回复信息。
交互服务层（API/React）：
main.py分发FastAPI入口，映射到8000端口上；chat.py通过API端口开辟Websocket实时通信通道；前端React框架通过8000端口进行数据传输，通过LoginPage等组件检验用户登录状态与信息进入理宝AI助手界面。
