## 分节 1

提示词工程实验探索报告
一、初始问题诊断
最初看到这个问题后，我实现了一个基于 “结构化提示词 + 自动化错误分类 + 线性
自修复” 的标准提示词工程框架。同时为了保证我后续能够方便进行迭代，我在我自己的
本地创建了 diagnosis.py 能够帮我生成三个 Turns 的输出与测试结果 json，这个诊断脚本可
以调用 solution 与 run 这两个代码，仅运行这个脚本就可以帮我完成输出结果整理与复盘。
在第一版中，我仅仅只是定义其角色与场景，告诉他输入的形式与他应该输出的格式，
并对于各种可能存在出现的问题（WA/RE/TLA）进行了分类讨论，并通过大模型辅助帮我完
成了全部的提示词构建，这里出现了的问题在于，我发现 Turn1-Turn3 三个阶段生成的测试
结果并不一致，发现到了测试模型拥有的上下文记忆有限，因此开始思考：这三个阶段的关
系分别是什么？怎么强化提示词以在这有限的三个阶段中物尽其用。
于是在第二版，我设计了用于协助模型结果回测思考的函数 execute_code，同时添加用
于对测试样例格式进行整理的函数，方便 LLM 收到的是纯净的题目描述；同时还修复逻辑
的“防御性”与“深度化”，在 _build_repair_message 中，引导策略变得更有针对性，从
“结果导向”转向“过程诊断”，对于 WA：不再只是说“结果错了”，而是引导模型进行
手动模拟执行流和检查 off-by-one errors。对于 RE：加入了对 traceback 的解读和 input
parsing 的二次检查。对于 TLE：明确给出了算法复杂度演进方向，而不仅仅是要求“快一
点”。
可以说在第二版中我对于各轮思考的衔接与输入进行了处理，但并没有对每一版的分别
处理，因此三轮都在"修修补补"同一个思路，如果算法本身就错了，修补是修不好的。考虑
到这个问题，我选择在第三版中做好差异化处理，我认为从这里开始我就思考要从思维链的
角度去修改这个提示词工程代码。
最终在第三版我规定了在每一轮都强制 LLM "先分析 → 再写代码"。且如果出现 WA，
应该在第 2、3 轮都 LLM 提示"换一种算法重写“，强制要求"换一种完全不同的算法重写"，
先分析旧方案为什么错，再用新思路。

二、策略演进历程
观察第三版的每一轮结果输出，我才终于反应过来，每一轮的结果都完全不同，可能第一轮
结果不错了，虽然有 WA，但也通过了部分测试样例，但是第二第三轮算法完全不同，导致
了错误率反而更高，结果因为只记录最后一版的结果所以这结果反而还不如第一轮的。因此
我开始结合我以前参与信息奥赛刷题的思路去进行思考，是否我要用有限的 token 与思考轮
次让模型在每一轮都思考不一样的解决方案吗？毕竟我自己做题也就是会看到题目->思考
解题方案->实践->修补循环，而现在每一轮的结果都不同，那不符合正常人解题的思路，所
以出错概率大也正常了。
因此在第四版之后，我开始重构我的提示词方案，最开始甚至更大胆，在 Turn1 把有限
的所有 token 都拿去思考，比较几个解题方案并得到最优方案，
不输出代码，把方案交给 Turn2

## 分节 2

于在这一版，第二轮负责生成代码和注释，最后第三轮根据代码与注释和相应的结果去进行
微调即可。第一轮思考，第二轮编程，第三轮微调，这样的流程也符合了人在思考题目时的
流程，同时也因为模型参数 Temperature 为 1，随机性极高，因此我也是通过这样的方式设
置逻辑锚点，避免后续两轮出现逻辑链断裂或思维链遗忘等问题。
但现在的问题就是，第一轮在思考上可冗余的余量太多了，还浪费了一次结果分析的机
会，因此我继续优化，在 solution.py 的提示词逻辑中增加以下硬性约束：强化输入解析的
“万能模板”指令，在 System Prompt 的 Implementation Rules 中加入对于 Python 语法的
强调，防止因为格式问题导致的 WA；增加“执行模拟”环节，要求模型在输出代码前，先
针对题目给出的 Example Input 进行模拟运行（如果 token 还有余量的话），solution.py 中
需要同步改动的逻辑点除了提示词文字，代码逻辑也应配合优化，最重要的点在于反馈截断
保护：如果 execute_code 返回的 feedback 特别长，模型会因上下文过载而胡言乱语。建
议在代码中强制截断 feedback 只保留前 1500 个字符 。由于 Temperature=1.0 可能导致
模型不输出闭合标签 ，在 _extract_code_block 中增加对“直到文本末尾”的匹配逻辑，确
保即使没有结尾的 ``` 也能提取出代码，并最重要的，将提示词改为全英文。
不过现在问题来了，我发现 Turn3 对于 Turn2 的修改过于少了，再输出上也显得偷工减
料，只是把代码的多余注释给删除或做了整理，缺少了 LLM 的反思（就跟我们人类做错题
会写错题本，会写反思检讨一样），因此怎么样在提示词正确引入“反思性思维链”很重要，
最开始我在 System Prompt 中要求模型必须先输出“Proof of Correctness（正确性证明）”
再写代码。
从结果分析来看，这样的反思性思维链并没有起到效果，但并不代表其不正确，因为这
是人脑思考方式中不可或缺的，所以一想到模型对对数字量化的敏感，我认为，可以对模型
进行规定，在 token 量足够的情况下（前提约束），
当模型对生成代码有 97%置信度能 70%pass
测试样例时，才开始生成代码。在这里我规定了一个置信度数字，确保在每一轮生成时，模
型有可量化的自信，同时这也只是我第一轮的 prompt，在后面我要求他 97%相信自己能做
到 95%pass（Turn2）,100%pass（Turn3），同时我对三轮的提示词策略进行修正，Turn 1 要
求深度思考 + Pilot Code（带重注释的原型代码），执行并获取结果，Turn 2 开始注重全新
上下文，只接收 T1 代码 + T1 结果 ，并进行优化注释，Turn 3 只接收 T2 代码 + T2 结果，
并限制严禁推翻算法，最小化改动。
但现在碰到的严重问题就是 RE，因为之前 WA 太多了，一碰到 RE 却还是第一版的思路，
所以在这个思维链下，如果 Turn1 的思路会 RE，则后面一直都是 RE，因此在这里我进行修
正，添加了在后续（T2\T3）轮次针对 RE 的改进，严格约束 RE 的独立性，无论 T2 还是 T3，
只要出现 RE，核心逻辑立即转向防御性编程（内存检查、递归限制、数据规模验证）。而
我又看了下 WA 的测试结果，根据 WA 可以看出模型的偷懒程度高，逻辑锚点可能过于深刻，
难以跳脱，我认为可以如果出现 WA->在 T2 加入深度思考的思维链：根据 T1 的代码进行深
度解析与回测并分析错误原因，T3 同样如此，也就是在 T2 再次迭代，主题逻辑不大变，但
需要一定脱离原来的思维捆绑，加入更多思考与逻辑解析(思考还未出现的情况，即反例与
特例）；T1 承担所有“脑力震荡”，要求 T1 必须做方案思考与对比。这保证了初始逻辑
的质量。T2 成为“诊断医生”，它的任务是解析与回测。它必须指出 T1 错在哪。通过“逻
辑回测”要求，强迫模型运行思维链来发现 T1 的锚点错误。T3 进化为“质检员”，专门
寻找极端反例（Corner Cases）。它会在 T2 已经修正的主逻辑上进行微调。

了大模型容易产生的“逻辑疲劳”：
T1 架构师模式 (The Architect)
重点强调 LOGIC COMPARISON（逻辑博弈）和 INVARIANTS（不变量分析）。
目的：强制模型在动笔前先在脑中“打草稿”，避免直接写出复杂度不达标或逻辑有误
的初版方案。
T2：取证审计师模式 (The Forensic Auditor)
重点：引入了 BREAK THE BIAS（打破偏见）和 DRY RUN（手动模拟）。
要求模型先输出 IMPROVEMENT PLAN 再写代码。这通过思维链（CoT）强迫模型承认
前一版的失败，并有针对性地进行逻辑转折，极大缓解了“逻辑锚定”问题。
T3：质检员模式 (The QC Inspector)
重点：执行 BOUNDARY SCAN（边界扫描）。
你提供了一个非常具体的 Checklist（溢出检查）。这让 T3 不再是无意义的微调，而
是一次对着清单进行的“外科手术式”加固。
也不再把原始的、乱糟糟的 feedback 直接丢给 LLM，而是做了一个中转层，通过分析
报错信息，提取出 RE 或 WA 的核心特征。如果可能的话（虽然代码中是占位符思路），
将通过率和失败样本信息结构化，这能给 T2/T3 提供极其明确的“审计坐标”。
同时在“防御性设计”上，使用了大量的“强约束”词汇，显著提升了指令的穿透力，
禁止项明确，DO NOT RECONSTRUCT（在 T3 除非准确率极低）防止了模型在最后一轮自乱
阵脚。输出格式硬化：Your response must contain ONLY the final code block，这在 T3 减少了
Token 浪费，也避免了 LLM 在文末废话导致的解析错误。物理规律锚定：在 T1 要求定义
Invariants（不变量），这是解决复杂模拟题的关键，防止模型理解错题目规则。
利用了 LLM 在被要求“寻找错误”时比“直接写对”更聪明的特点，通过审计和清单
机制，模拟人的思维链，也让我更加理解了 AI 开发的意义。
