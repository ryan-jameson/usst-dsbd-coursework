## 分节 1

实验四：课程设计
题目：校园跑步路径规划问题
一、摘要
本实验围绕校园跑步打卡中“给定打卡点如何规划最优访问顺序”和“如何生成低聚集的新打卡点”两个问题展开。依据附件中的上海理工大学校园道路图和打卡点坐标数据，本文先从地图图片中识别道路区域，将道路骨架转化为图模型，再在图模型上完成打卡点投影、最短路计算、访问顺序优化、候选点生成和多组路线拥挤度控制。
模型设计采用“两层道路图”的思想：第一层为由图像骨架提取得到的细道路段图，用于保留地图道路的几何形状和像素尺度长度；第二层为粗道路图，用不超过 50 个空间分散的代表路口或端点描述校园主要通行结构，并将“相邻打卡点不超过 3 条道路”解释为粗道路图上的约束。对于给定 5 个打卡点，枚举 5! = 120 种访问顺序，选择总距离最短且满足道路数约束的路线；对于 10 组新打卡点生成，分别构造完全随机、可行性优先随机、贪心低聚集和多目标低聚集算法进行比较。实验结果表明，多目标低聚集算法能够在 10 组打卡数据全部可行的前提下，将共享粗道路数降为 0，最大路段负载降为 1，具有更好的路线分散效果。
二、问题重述
跑步打卡系统为学生随机生成 5 个打卡点，学生可以按照任意顺序跑到这些点，并通过卫星定位完成打卡。由于相邻两次打卡之间存在时间限制，打卡点的空间分布和访问顺序都会影响完成效率，本实验需要解决两个子问题：
子问题 A：给定 5 个打卡点后的路径规划，输入一组 5 个打卡点；输出访问顺序、最短路线、总路程、最大相邻道路段数、最大相邻时间；先计算两两最短路，再枚举 `5! = 120` 种访问顺序；作为可行性检验器和给定 5 点下的最优访问顺序求解器。
子问题 B：随机生成 10 组新的打卡点，输入校园道路段拓扑图和候选打卡点池；输出10 组打卡点，每组 5 个点；其中每组必须存在至少一条访问顺序，使相邻打卡点之间不超过 3 条道路；优化目标为减少不同组路线之间的共享道路段，降低同时跑步时的聚集风险。穷举法不能直接解决打卡点生成问题，因为它只能枚举给定 5 点的访问顺序，不能从整个校园候选点池中穷举选 5 点。若候选点池有 `N` 个点，直接枚举组合需要检查 `C(N,5)` 组，组合数量会迅速变得不可接受。因此，本实验将穷举法作为内部精确检验器，而不是最终生成算法。
三、算法设计
3.1 地图道路识别
地图图例显示，道路和停车场主要为白色区域，绿化、建筑、水域等区域颜色饱和度较高。本文采用如下流程识别道路：先将原图按比例缩小，提高计算效率，再转换到 HSV 颜色空间，用高饱和度区域定位校园主体范围，并通过膨胀、闭运算和孔洞填充获得校园包络，在校园包络内部提取低饱和度、高亮度区域作为道路候选区域，对道路区域进行骨架化，得到单像素宽度的道路中心线，将骨架像素构造成加权无向图，边权为原图像素尺度下的欧氏距离。

图3 地图识别处理可视化展示
像素级路网足够精细，但不适合表达“经过几条道路”。因此在像素骨架图基础上构造道路段拓扑图度数不等于 2 的骨架节点视为路口或端点；两个路口之间连续的一段骨架视为 1 条道路段；道路段边权为该段骨架在原图像素尺度下的长度。后续打卡点生成和 3 条道路约束都基于这个道路段拓扑图。为使“经过几条道路”的含义更接近实际校园道路，而不是图像骨架中的细碎像素段，本文进一步构造两层图结构。第一层为细道路段图 H：将度数不等于 2 的骨架节点视为路口或端点，两个相邻路口之间的连续骨架视为一条细道路段。第二层为粗道路图 ROUTE_GRAPH，从 H 中选取不超过 50 个空间分散的代表路口或端点，并把代表节点之间在 H 上的最短连接路径压缩为一条粗道路。后续候选点选择、3 条道路约束、拥挤度统计和生成算法均基于粗道路图完成。
3.2 路径规划模型
设粗道路图为[G=(V,E)]，其中 (V) 表示候选打卡点、路口或道路端点，(E) 表示道路段。对任意道路段 (e∈E)，记其长度为(le)。对于任意两个打卡点 (pi,pj)，定义：[d(pi,pj)=minρ:pi→pje∈ρle]，其中 (d(pi,pj)) 表示两点之间在道路图上的最短路径长度；同时定义[h(pi,pj)]，为两点最短路径经过的粗道路段数量。题目中“每两个打卡点间不超过 3 条道路”的约束可表示为：[h(pi,pj)≤3]。由于 5 个点数量较少，可直接枚举所有 5! 种访问顺序，选择总距离最小的顺序：minπ k=14d(Pπk,Pπk+1)，其中 π 是 5 个打卡点的一个排列，排列中任意相邻两点之间经过的粗道路数均不超过 3，则认为该访问顺序可行；在所有可行顺序中，选择总路程最短的方案。该模块返回最优顺序、总距离、最大相邻道路数、最大相邻距离、完整边路径和已使用道路集合，是后续生成算法的内部可行性检验器。
3.3 打卡点生成算法
候选打卡点直接取自粗道路图 ROUTE_GRAPH 的节点，数量控制在 50 个以内，且最近候选点间距约为 308.42 像素，避免点位过密。打卡点生成问题与给定 5 点后的访问顺序优化不同。若候选点池共有 (M) 个点，则从中选出 5 个打卡点的组合数量为：[CM5=M!5!(M−5)!]，当 (M) 较大时，组合数量会迅速增长，无法直接穷举所有可能点组。
为比较不同打卡点生成算法的效果，本文将评价指标分为两类：约束性指标和性能评价指标。首先，所有生成结果必须满足基本约束：每组包含 5 个打卡点，且存在至少一条访问顺序，使相邻打卡点之间经过的粗道路数不超过 3。该约束用于判断算法生成结果是否可用。在满足约束的基础上，本文进一步选取 5 个核心指标比较不同算法的性能：① 平均总路径长度[L=1Ng=1NLg]，其中，(Lg) 表示第 (g) 组路线的总路径长度，(N) 为生成组数。该指标越小，说明路线整体越短。② 总共享道路段数[S=e∈EI(qe≥2)]，其中，(qe) 表示道路段 (e) 被多少组路线使用，(I(⋅)) 为示性函数。该指标越小，说明不同组之间路线重叠越少。③ 最大道路段负载[Qmax=maxe∈Eqe]，该指标表示单条道路最多被多少组路线共同使用。数值越小，说明不存在明显的局部聚集。④ 拥挤指数[C=e∈Eqe2]，该指标采用平方惩罚，能够放大高频重复道路的影响。若某些道路被多组路线反复使用，拥挤指数会明显升高。⑤ 平均运行时间[T=1Ng=1NTg]该指标用于衡量算法计算效率。运行时间越短，算法效率越高；但若算法能够显著降低聚集，适当增加运行时间是可以接受的。
因此，本文采用“候选点随机生成 + 可行性检验 + 拥挤度评价 + 多目标优化”的思路：先生成候选点组，再调用路径规划模块判断是否可行，最后根据路线长度和聚集程度选择更优方案。本文设置三个基准算法：完全随机生成、可行性优先随机生成和贪心低聚集生成。完全随机生成算法直接从候选点池 (Vc) 中随机选择 5 个点：[Sg∼Random(Vc,5)]，该方法不考虑可行性约束，也不考虑路线聚集问题，因此作为最弱基准。可行性优先随机算法仍然随机生成候选点组，但只保留满足约束的组合：[F(Sg)=1, Hg≤3]，其中 (F(Sg)=1) 表示该点组存在至少一条可行访问顺序。该算法能够提高约束满足率，但没有主动减少不同组路线之间的重合。贪心低聚集算法逐组生成打卡点。对于第 (g) 组，先生成若干个可行候选组 (Ωg)，再选择与已有路线共享道路段最少的组合：[Sg∗=argminS∈Ωg|E(S)∩Eused|]，其中 (E(S)) 表示候选路线经过的道路段集合，(Eused) 表示前 (g−1) 组路线已经使用过的道路段集合。该算法能减少部分路线重叠，但每次只做局部选择，可能陷入贪心局限。改进算法 MultiObjectiveLowCongestionGenerator 采用“候选池采样 + Beam Search + 局部替换搜索”的思想，每次生成若干可行候选组，按目标函数筛选较优方案，再尝试局部替换其中一个打卡点。对于候选点组 (S)，定义综合目标函数：[J(S)=w1L(S)+w2Shared(S)+w3Qmax(S)+w4Repeat(S)+w5Penalty(S)+w6|E(S)|]，其中，[L(S)=L(S)Lnorm]表示归一化路线长度；[Shared(S)=|E(S)∩Eused|]表示当前路线与已有路线的共享道路段数量；[Qmax(S)=maxe∈E(S)(qe+1)]表示加入当前路线后的最大道路负载；[Repeat(S)]表示候选点与已生成打卡点重复或过近的惩罚；[Penalty(S)]表示不可行惩罚。若候选点组不存在满足 (Hg≤3) 的访问顺序，则赋予极大惩罚；[|E(S)|]表示路线使用的道路段数量，用于抑制过长或过复杂路线。因此，目标算法的优化模型为：[minSJ(S)][s.t. F(S)=1, H(S)≤3]。与三个 baseline 相比，多目标低聚集算法的优势在于其评价标准更加全面。完全随机算法不考虑可行性和聚集性；可行性优先随机算法只保证路线可行，但不控制路线重叠；贪心低聚集算法只关注当前路线与已有路线的共享道路段，容易忽略最大道路负载和整体路线复杂度。
本文算法同时考虑路线长度、共享道路段、最大道路负载、重复点位和不可行惩罚。其中，最大道路负载项能够避免多组路线集中经过同一条道路，重复点位惩罚能够避免打卡点过于集中，不可行惩罚保证算法优先生成满足 3 条道路约束的点组。因此，该算法更符合“同时发生的跑步路线尽可能减少聚集”的题目要求。
四、结果检验
结果检验分为两部分。第一部分检验给定打卡点后的路径规划能力，即模型是否能够根据已有打卡点计算合理访问顺序和实际路径。第二部分检验打卡点生成算法，即系统随机生成的 10 组新打卡点是否全部满足“相邻打卡点之间不超过 3 条道路”的约束，并进一步比较不同算法生成路线的聚集程度。在算法对比中，若某算法具有更高的约束满足率、更少的共享道路段、更低的最大道路负载和更低的拥挤指数，则说明该算法在可行性和低聚集性方面表现更优。

五、总结与讨论
从算法对比结果看，完全随机算法虽然能够生成部分可行组合，但路线重叠较明显，总共享道路段数为 31，最大道路负载为 4，拥挤指数为 164；可行性优先随机算法能提高约束满足效果，但仍存在共享道路段数较高的问题，总共享道路段数为 21，最大道路负载为 3，拥挤指数为 118。贪心低聚集算法明显改善拥挤情况，总共享道路段数降为 1，最大道路负载为 2，拥挤指数为 49。
从结果可以看出，算法性能的提升具有明显层次性。完全随机算法由于缺少约束控制，路线重叠最明显；可行性优先随机算法虽然改善了可行性，但共享道路段数仍然较高，说明“可行”并不等于“低聚集”。贪心低聚集算法通过减少当前路线与已有路线的重叠，使共享道路段数大幅下降，但最大道路负载仍为 2，说明仍存在局部重复使用道路的情况。
相比之下，多目标低聚集算法将总共享道路段数降为 0，最大道路负载降为 1，说明 10 组路线之间基本没有重复使用同一粗道路段。虽然其拥挤指数 48 与贪心算法 49 接近，但最大负载和共享道路段数进一步降低，说明其路线分散性更好。该结果证明，多目标函数中的共享道路惩罚和最大道路负载惩罚能够有效引导算法避开已被使用的道路。虽然多目标低聚集算法生成 10 组打卡点的总运行时间约为 6.70 秒，平均每组约为 0.67 秒，高于简单贪心算法，但这是为了同时考虑路线长度、共享道路、最大负载和点位分散性所付出的计算代价。
本模型的优点在于将图像处理、图论最短路、访问顺序优化和多目标低聚集生成结合在同一框架中，并将“道路”从像素骨架进一步粗化为更符合实际理解的粗道路图，使候选点不会过密，约束含义更加清晰。模型的不足主要包括：道路识别仍依赖地图颜色阈值，若地图风格变化较大需要重新调整参数；跑步时间估计仅采用固定米/像素比例和平均速度，尚未考虑上下坡、拥堵、红绿灯或 GPS 漂移等实际因素；此外，目标函数权重目前根据经验设定，后续可以结合真实打卡数据进一步标定。
综上，本文将穷举法用于给定 5 点后的精确路径规划，将多目标低聚集算法用于反向生成打卡点，实现了“路径可行性检验”和“低聚集点位生成”的分工。实验结果表明，目标算法相较 baseline 能在保证 10 组打卡数据全部可行的同时，进一步降低共享道路段数和最大道路负载，因此更适合作为校园跑步打卡系统的自动打卡点生成方法。

1. 给定 5 点后的最优访问顺序规划函数
def plan_route_for_points(points, segment_graph, distance_cache=None, max_segment_count=MAX_SEGMENT_COUNT):
    nodes = [point_to_node(point) for point in points]
    pair_info = {}
    for i, j in permutations(range(len(nodes)), 2):
        if i < j:
            pair_info[(i, j)] = pair_shortest_path_info(nodes[i], nodes[j], segment_graph, distance_cache)
    best = None
    for order in permutations(range(len(nodes))):
        total_distance, max_count, edge_path = 0.0, 0, []
        feasible = True
        for left, right in zip(order[:-1], order[1:]):
            info = pair_info[tuple(sorted((left, right)))]
            if info['road_count'] > max_segment_count:
                feasible = False
                break
            total_distance += info['distance']
            max_count = max(max_count, info['road_count'])
            edge_path.extend(info['edge_path'])
        if feasible and (best is None or total_distance < best['total_distance']):
            best = {'feasible': True, 'order': order, 'total_distance': total_distance, 'max_segment_count': max_count, 'edge_path': tuple(edge_path), 'used_edges': frozenset(edge_path)}
    return best if best is not None else {'feasible': False}

def objective_value_for_plan(plan, candidate_ids, edge_loads, selected_coords, distance_norm, weights=None):
    weights = weights or {'w1': 1.0, 'w2': 5.0, 'w3': 10.0, 'w4': 3.0, 'w5': 1e6, 'w6': 0.8}
    if not plan['feasible']:
        return weights['w5']
    normalized_total_distance = plan['total_distance'] / distance_norm
    shared_edge_count = route_shared_edge_count(plan, edge_loads)
    max_edge_load = route_max_edge_load_after(plan, edge_loads)
    repeated_penalty = repeated_point_penalty(candidate_ids, selected_coords)
    return (weights['w1'] * normalized_total_distance + weights['w2'] * shared_edge_count + weights['w3'] * max_edge_load + weights['w4'] * repeated_penalty + weights.get('w6', 0.0) * len(plan['used_edges']))

class MultiObjectiveLowCongestionGenerator:
    def generate(self):
        records = []
        for group_id in range(1, self.n_groups + 1):
            pool = []
            while len(pool) < self.batch_size and local_attempts < self.max_attempts_per_group:
                item = self.random_feasible_candidate()
                if item is not None:
                    pool.append(item)
            pool.sort(key=lambda item: item['objective'])
            best = min((self.local_search(item, group_id) for item in pool[:self.beam_width]), key=lambda item: item['objective'])
            records.append(group_record('MultiObjectiveLowCongestion', group_id, best['candidate_ids'], best['plan'], self.edge_loads.copy(), best['objective']))
            update_edge_loads(self.edge_loads, best['plan'])
            append_selected_coords(self.selected_coords, best['candidate_ids'])
        return records
