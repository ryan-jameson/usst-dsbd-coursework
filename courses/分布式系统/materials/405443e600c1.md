四、实验原理
RMI: 远程方法调用(Remote Method Invocation)，它支持存储于不同地址空间的程序级对象之间彼此进行通信，实现远程对象之间的无缝远程调用。
Java RMI: 用于不同虚拟机之间的通信，这些虚拟机可以在不同的主机上、也可以在同一个主机上；一个虚拟机中的对象调用另一个虚拟上中的对象的方法，只不过是允许被远程调用的对象要通过一些标志加以标识。
RMI远程调用步骤：

RMI由3个部分构成，第一个是rmiregistry（JDK提供的一个可以独立运行的程序，在bin目录下），第二个是server端的程序，对外提供远程对象，第三个是client端的程序，想要调用远程对象的方法。
首先，先启动rmiregistry服务，启动时可以指定服务监听的端口，也可以使用默认的端口（1099）。
其次，server端在本地先实例化一个提供服务的实现类，然后通过RMI提供的Naming/Context/Registry（下面实例用的Registry）等类的bind或rebind方法将刚才实例化好的实现类注册到rmiregistry上并对外暴露一个名称。
最后，client端通过本地的接口和一个已知的名称（即rmiregistry暴露出的名称）再使用RMI提供的Naming/Context/Registry等类的lookup方法从RMIService那拿到实现类。这样虽然本地没有这个类的实现类，但所有的方法都在接口里了，便可以实现远程调用对象的方法了。
客户端体系结构：
（1） stub层：负责解释客户程序发出的远程方法调用；然后将其转发到下一层 
（2） 远程引用层：解释和管理客户发出的到远程服务对象的引用，并向下一层即传输层发起IPC操作，从而将方法调用传送给远程主机 
（3） 传输层：基于TCP协议 
服务器端体系结构：
（1） skeleton层：负责与客户端stub进行交互 
（2） 远程引用层：管理源于客户端的远程引用，并将其转换成能被skeleton层理解的本地引用 
（3） 传输层：与客户端体系结构一样，面向传输层。

import java.rmi.registry.LocateRegistry;
import java.rmi.registry.Registry;
import java.util.List;

/**
 * RMI 客户端主程序，按序测试增删改查。

public class RMIClient {
    public static void main(String[] args) {
        try {
            // 连接本地 1099 端口的注册表
            Registry registry = LocateRegistry.getRegistry("localhost", 1099);
            IRemoteStudentService service = (IRemoteStudentService) registry.lookup("StudentService");

            // 添加两个测试学生
            Student s1 = new Student("2023001", "Alice", 90, 95, 88);
            Student s2 = new Student("2023002", "Bob", 85, 80, 92);
            service.addStudent(s1);
            service.addStudent(s2);
            System.out.println("添加完成：" + service.getAllStudents());

            // 查询单个
            System.out.println("查询 2023001 => " + service.queryStudent("2023001"));

            // 修改分数
            Student updated = new Student("2023001", "Alice", 95, 96, 93);
            service.updateStudent(updated);
            System.out.println("修改后查询 2023001 => " + service.queryStudent("2023001"));

            // 删除一个
            service.deleteStudent("2023002");
            System.out.println("删除 2023002 后，所有学生 => " + service.getAllStudents());

            // 再次查询已删除的记录
            System.out.println("查询 2023002（应为 null） => " + service.queryStudent("2023002"));

        } catch (Exception e) {
            System.err.println("客户端调用异常: " + e.getMessage());
            e.printStackTrace();
        }
    }
}

2. 每个文件主要实现的功能和文件相互间的关系 
基础模型与接口
Student.java (学生实体类)
功能：定义了学生的基本属性（学号、姓名、数语英成绩）。
核心特性：实现了 java.io.Serializable 接口。因为在 RMI 分布式调用中，客户端和服务端不在同一个 JVM 内存里，对象必须“序列化”变成字节流才能在网络（TCP）中传输。
IRemoteStudentService.java (远程调用接口)
功能：继承了 java.rmi.Remote，定义了所有的服务方法（addStudent, deleteStudent, updateStudent, queryStudent, getAllStudents）。
关系：它是连接客户端和服务端的契约。客户端拿着这个接口去调用，服务端负责实现这个接口的逻辑。
服务端核心 (处理业务与数据库交互)
RemoteStudentServiceImpl.java (服务提供者/实现类)
功能：继承 UnicastRemoteObject，真正实现了接口里的增删改查逻辑。
关系：它负责在构造时读取根目录的 .env 文件，加载 MySQL 账户密码；当客户端调用增删改查等方法时，由它负责加载 mysql-connector，通过 JDBC 将 SQL 语句发送给本地真实的 MySQL 数据库并把结果打包返回。
RMIServer.java (服务端启动器与监控视窗)
功能：这是服务端的主入口（包含 main 方法）和图形化控制台。
关系：它负责在 1099 端口启动 RMI 注册表（Registry），并将实例化好的 RemoteStudentServiceImpl 绑定（bind）到名字为 "StudentService" 的目录项上，原地等待客户端的请求。同时它劫持了控制台输出，将系统日志展示在图形界面上。
客户端核心 (面向用户的操作终端)
RMIClient.java (客户端图形化交互程序)
功能：客户端的主入口（包含 main 方法），提供了一个基于 Java Swing 的业务操作窗口。
关系：客户端在启动时，会通过局域网/本机地址和 1099 端口连接 RMI 注册表，通过 lookup("StudentService") 查找到服务端的代理对象（Stub）。
交互：用户在界面上输入表单并点击按钮触发事件 -> 客户端调用代理对象的方法并将 Student 对象传过去 -> RMI 底层通过网络将操作发给服务端的 RemoteStudentServiceImpl -> 服务端操作数据库后一层层把运行结果或数据返回给客户端界面显示。

4. 试验运行情况和结果，在试验中遇到的问题和分析 

问题 1：早期的 HashMap 内存存储仅进行内部数据结构存放
现象与原因： 在最初的版本中，RMI 服务端的 RemoteStudentServiceImpl 是通过声明一个 Map<String, Student> store = new HashMap<>() 来存放学生数据的。这导致如果服务端程序被关闭或发生崩溃，存储在内存中的所有学生测试数据都会丢失，不符合真实的生产级分布式系统的存储规范。
分析与解决： 必须引入真实的关系型数据库来进行数据的存取操作。
设计了 init.sql 脚本来标准化 MySQL 数据库引擎、表结构（student表）的创建以及基础测试样例的注入。
彻底重构了 RemoteStudentServiceImpl，废弃 HashMap 方案，改为直接集成 java.sql.* (JDBC) 的包，在每一个 add、update、delete、query 操作被调用时，实时利用 Connection 对 MySQL 发送原生的 DML / DQL 语句，达到数据完全持久化的目的。
问题 2：硬编码数据库凭证导致代码耦合度高且不安全
现象与原因： 如果将 MySQL 的连接 url、账号、密码等字符串直接写死在 Java 代码内，不仅不安全，还导致本地环境稍微产生变化（比如换了一台电脑运行或者更改了数据库密码），就需要重新修改源代码甚至重新执行 javac 编译。
分析与解决： 借用现代 Web 开发常用的环境变量理念进行解耦。
在项目的根目录下独立创建了 .env 配置文件用于暴露配置（使用 Properties 格式）。
在服务端的构造函数初始化时，使用 FileInputStream 动态加载 .env 属性。
此举做到了即便之后将代码交给其他同学测试，对方只需修改外部的 .env 即可正常运行，完美剥离了核心代码与私密运行环境的耦合。
问题 3：编译/运行时出现找不到驱动程序异常
现象与原因： 修改代码引入数据库代码后，在终端手动执行 javac 和 java 操作并尝试进行包含数据库操作的访问时，程序抛出无法找到 com.mysql.cj.jdbc.Driver 或无法识别 JDBC 的报错。其原因是因为纯净的 JDK 本身不携带具体厂商的直连协议依赖。
分析与解决：
手动下载并准备了 mysql-connector-java-8.0.x.jar 的第三方外部驱动包。
在包含该 jar 包运行时，必须在编译与执行时携带 -classpath 参数（例如 -cp "exp4/out;exp4/lib/mysql-connector.jar"），目的是强制告诉 Java 虚拟机的类加载器，从指定的路径把第三方通信包也装载进内存中去，从而顺利连通 MySQL 数据库底层。
问题 4：终端日志操作不够直观，无法有效监控交互状态
现象与原因： 采用纯命令行时，必须开启多个黑窗口（Terminal），所有数据无论是客户端的用户查询还是服务端发起的 SQL 命令操作痕迹都穿插在各种控制台内，界面交互差，难以作为成型的软件进行系统级演示。如果在启动后被遮挡，更会遇到“误以为点击了没反应”的情况。
分析与解决：
利用 Java 原生的 Swing 工具包，将 RMIServer 和 RMIClient 全部重写为带 GUI 可视化视窗界面的 Windows 桌面程序容器。
客户端中增加了文本框验证与事件监听器，让增删改查具备表单化提交体验和异常捕获弹窗。
服务端利用高级技术 “重定向 System.out 和 System.err（日志劫持）”，将底层的 println 打印直接渲染到服务端的 JTextArea 控件内，做到了一个完美的实时分布式监控主面板。
问题 5：开发过程复杂导致运行测试门槛过高
现象与原因： 当前涉及的工作流由于拆分严密，要想测试一次 RMI 系统，需要先按复杂的带参数语句编译项目，再开一个终端运行服务端并等待端口绑定完毕，最后再开另一个终端运行客户端。如果是纯手工操作很容易漏掉步骤或者搞反顺序。
分析与解决： 编写了专属基于 Windows 系统的自动化构建与测试部署脚本 run.bat。该脚本负责全自动检测环境、使用 -cp 携包编译所有的源代码、通过 start 指令开辟独立线程启动监控服务端、并在巧妙 timeout 两秒给予端口挂载时间后自动拉起用户客户端。将多重复杂指令缩略到了一个图标的“傻瓜式一键运行”，大幅提高了之后实验验证与迭代调试的效率。
七、思考题  
1. 如何使用RMI传递参数？ 
在 RMI调用过程中，因为客户端和服务端位于不同的 Java 虚拟机，甚至不同的物理机器上，所以无法直接共享内存。因此，无论什么参数被传入 RMI 方法，都必须经过网络传输。RMI 传递参数主要依据：值传递或引用传递。（对象、操作）前者适用于基本数据类型和普通对象，对于基本数据类型，RMI 会自动将它们打包为字节流发送过去。对于普通对象（Student 类），这类对象必须实现 java.io.Serializable 接口。当客户端将 Student 对象做为参数传递时，RMI 底层会将该对象的整个属性值序列化成跨平台的字节流，传送到服务端后，再反序列化重构出一个完全一模一样的新对象。因此，服务端对这个参数对象的任何纯本地修改，不会影响客户端的原对象（相当于拷贝了一份）。
后者适用于远程对象本身，如果传递的参数本身也是一个实现了 java.rmi.Remote 并被 UnicastRemoteObject 服务化导出的对象，那么传输的将不仅仅是数据副本，而是一个存根。服务端拿到这个存根后，调用它内部的方法时，实际上会反向发起网络请求回到客户端来执行。这就相当于传递了一个远程“指针”。
2. 如何使得被动提供远程服务的服务器能够主动发起数据请求？ 
使用 RMI 的回调 (Callback) 机制，定义客户端的 Remote 接口：不仅服务端要有接口，客户端也需要定义一个派生自 java.rmi.Remote 的接口，并在里面定义接收服务端推送数据的方法（如 void receiveMessage(String msg) throws RemoteException）。这样能让客户端导出自己并注册客户端实现这个接口，并通过 UnicastRemoteObject.exportObject() 将自己暴露在网络上，使得客户端同时变成了一个“微型服务端”。通过参数传递代理指针：在服务端的核心接口中，增加一个类似于 registerCallback(IClientCallback client) 的方法。客户端在最初连接服务端时，将“自己”当作参数传给服务端。因为传递远程对象是引用传递，所以服务端保存了这些客户端的代理存根。当服务端要主动发送数据时，遍历这些存根，像调用本地方法一样调用 client.receiveMessage(data)，这就实现了由受变主的“反向调用”。
3. 如何避免在多个客户端同时发起远程服务调用时产生不一致的情况？ 
可以使用synchronized关键字加锁，像在本实验中的类一样，在所有的增、删、改方法前加上synchronized关键字。这会为该远程对象加锁。当 Client A 调用方法时，如果 Client B 恰好同时发起修改请求，由于锁的存在，B 所在的线程会被阻塞等待，直到 A 处理完毕释放锁。这样就保证了请求是原子性地依次执行的。
如果启动了多个服务器实例，Java 层的锁有时不够，此时需要依赖数据库层的事务和锁机制，将 JDBC 的自动提交关闭（ HYPERLINK "vscode-file://vscode-app/USER_HOME/AppData/Local/Programs/Microsoft VS Code/resources/app/out/vs/code/electron-browser/workbench/workbench.html" \o "" conn.setAutoCommit(false)），并将一系列操作组合成一个事务。设置隔离级别如REPEATABLE READ或者串行化，防止数据操作到一半时被别人读取。
对于强一致性操作，可以使用 SQL 级别自带的控制，比如加写锁（SELECT ... FOR UPDATE），这也能彻底从底层保证多个发起源头对同一行数据（例如同一个学生成绩）的修改绝不会出现并发错误重叠。

四、实验原理  
基于http的web应用是分布式系统的另一个重要应用范型，与C/S模式不同的是B/S模式的应用没有独立的客户端软件，B/S模式中统一对服务器端响应进行解释的就只有浏览器。因为浏览器的通用性的简单性，使得B/S应用中数据传递也不可能很复杂，因此就决定了它在应用层的支持协议只能是面向文本的http协议。 
最初的http协议只能支持简单的静态页面（对象）的获得，但是随着网络应用的发展，提供与客户的接口，使得客户与服务器端的通信能够动态进行，并由此动态生成页面（对象）是必要的。解决这一问题的主要手段是使用表单技术。而保存与客户交互的结果也是必须的，解决的技术是cookie。

1. 论述HTTP协议的通信原理
通信前，客户端先通过 Socket 向目标服务器的指定端口发起连接请求，完成完整的 TCP 三次握手流程：客户端先发送 SYN 同步报文，服务端收到后回复 SYN+ACK 同步确认报文，客户端最终返回 ACK 确认报文，至此建立起可靠的全双工字节流通道，彻底规避底层传输的丢包、乱序问题，这是所有 HTTP 通信能够稳定执行的前置基础。连接建立后，客户端严格遵循 HTTP 协议规范逐段构建标准化请求报文，通过sendMessage () 方法完成报文的有序发送：先拼接核心请求行，明确请求方法、资源路径与 HTTP 版本号，再按行拼接 Host、Connection 等必填请求头字段，随后写入协议强制要求的单独 \r\n 空行标识请求头结束；针对 POST 请求，还会先将表单数据转为 UTF-8 字节流，计算准确的 Content-Length 长度值，补充 Content-Type 字段标注数据格式，再将请求体完整写入输出流，所有报文段均以 \r\n 作为行分隔符，全程兼容 HTTP/1.0 与 HTTP/1.1 双版本规范。
服务端从 Socket 输入流中完整接收报文后，按协议规则反向解析：先读取请求行拆分核心请求信息，再逐行读取请求头直至识别到空行，最后根据 Content-Length 读取对应长度的请求体，解析完成后执行静态资源读取、表单数据处理、CGI 脚本调用等对应业务逻辑，再按相同规范构建包含状态行、响应头、空行与响应体的标准化响应报文，通过已建立的 TCP 连接回传至客户端。客户端通过 receiveMessage () 方法完成响应的全流程解析：先读取状态行确认请求处理结果，再逐行解析响应头，提取 Content-Type、Content-Length 等核心元数据，依据长度值精准读取完整响应体，避免 TCP 粘包导致的数据缺失，最终根据内容类型完成网页渲染或数据展示。
通信结束后，HTTP/1.0 默认采用短连接模式，单次请求 - 响应闭环完成后，客户端与服务端立即通过 TCP 四次挥手关闭连接，完整释放 Socket 相关资源；HTTP/1.1 则默认启用长连接模式，通过 Connection: keep-alive 字段控制，可在同一条 TCP 连接中承载多次请求 - 响应交互，大幅降低重复握手挥手带来的性能开销。

七、思考题  
1. 考虑隐式表单域与cookie技术之间的区别 
首先，在存储位置与作用域上，隐式表单域以 <input type="hidden"> 标签形式嵌入 HTML 源码中，仅对当前页面有效；而 Cookie 存储于客户端本地并与特定域名绑定，具备跨页面共享的能力。其次，两者的传输方式截然不同：隐式表单域必须由用户主动提交表单才能随请求体或 URL 发送，属于被动触发；Cookie 则由浏览器自动管理，一旦服务器通过 Set-Cookie 响应头设定，后续对该域名的所有请求均会自动在请求头中携带 Cookie 字段，无需用户干预。在生命周期方面，隐式表单域随页面关闭或刷新即失效，而 Cookie 可通过 Expires 或 Max-Age 属性实现会话级甚至持久化存储。此外，容量限制上隐式表单域主要受限于服务器接收能力，理论上限较高，而 Cookie 则受到严格的单条 4KB 及数量限制。最后从安全性考量，隐式表单域直接暴露于页面源码中极易被篡改，Cookie 虽可通过 HttpOnly 属性防止脚本窃取，但仍需额外防范网络窃听与伪造攻击。
2. 考虑cookie的安全性问题 通过实验socket抓包发现，Cookie 以明文形式附带在 HTTP Header 中传输，易出现明文窃听，HTTP/1.0 无加密，抓包工具可截获 Cookie。；同时还容易遇到跨站脚本攻击，恶意脚本可通过 document.cookie 窃取 Cookie。且浏览器自动携带 Cookie，攻击者可诱导用户发起伪造请求。对于客户端来说，用户可修改本地 Cookie 提权。

一、实验目的及要求

要求：要求独立完成。 
二、实验原理和步骤 
1.实验原理 
（1）服务器主要监听来至客户浏览器或是客户端程序的连接请求，并且接收到客户请求后对客户请求作出响应。如果请求是静态的文本或是网页则将内容发送给客户。如果是 CGI 程序则服务器调用请求的 CGI 程序，并发送结果给客户。 
（2）HTTP 协议是基于 TCP/IP 协议之上的协议，是 Web 浏览器和 Web 服务器之间的应用层协议，是通用的、无状态的、面向对象的协议。 
（3）HTTP 的请求一般是 GET 或 POST 命令（POST 用于 FORM 参数的传递）。GET 命令的格式为 
GET 路径/文件名 HTTP/1.0 
文件名指出所访问的文件，HTTP/1.0 指出 Web 浏览器使用的 HTTP 版本。 
（4）Web 浏览器提交请求后，通过 HTTP 协议传送给 Web 服务器。Web 服务器接到后，进行事务处理，处理结果又通过 HTTP 传回给 Web 浏览器，从而在 Web 浏览器上显示出所请求的页面。 
在发送内容之前 Web 服务器首先传送一些 HTTP 头信息： 
HTTP 1.0 200 OK 
WEBServer：1.0 // 服务器类型 
content_type:类型 
content_length:长度值 
（5）响应 POST 和 GET 命令的 CGI 程序调用请求需要服务器执行外部程序，Java 执行外部可执行程序的方法是：首先通过 Runtime run = Runtime.getRuntime()返回与当前 Java 应用程序相关的运行时对象；然后调用 Process CGI = run.exec(ProgramName)另启一个进程来执行一个外部可执行程序。 
2. Web 服务器的实现步骤： 
(1) 创建 ServerSocket 类对象，监听端口 8080。这是为了区别于 HTTP 的标准 TCP/IP端口 80 而取的; 
(2) 等待、接受客户机连接到端口 8080，得到与客户机连接的 socket;
(3) 创建与 socket 字相关联的输入流和输出流 

(4) 从与 socket 关联的输入流 instream 中读取一行客户机提交的请求信息，请求信息的格式为：GET 路径/文件名 HTTP/1.0 

(5) 从请求信息中获取请求类型。如果请求类型是 GET，则从请求信息中获取所访问的文件名。没有 HTML 文件名时，则以 index.html 作为文件名； 

如果请求文件是 CGI 程序存则调用它，并把结果通过 socket 传回给 Web 浏览器，（此处只能是静态的 CGI 程序，因为本设计不涉及传递环境变量）然后关闭文件。否则发送错误信息给 Web 浏览器； 

(7) 关闭与相应 Web 浏览器连接的 socket 字。

// public/app.js: startTraining 方法
async function startTraining() {
    // 获取用户选择的 题目类型和 难度
    const topic = topicSelect.value;
    const difficulty = difficultySelect.value;
    try {
        // 构造请求负载
        const payload = { topic, difficulty };
        
        // 使用 Fetch API 向后端 CGI 程序发起异步 POST 请求
        // URL: /cgi-bin/QuestionSelector (Python 脚本)
        // 作用：告诉服务器 "我要做一个这种类型的题目，请生成数据给我"
        const response = await fetch('/cgi-bin/QuestionSelector', {
            method: 'POST',
            headers: { 'Content-Type': 'application/json' },
            body: JSON.stringify(payload)
        });
        // 解析服务器返回的 JSON 格式题目数据
        const text = await response.text();
        currentTask = JSON.parse(text); // 将 JSON 字符串转换为 JS 对象
        // 拿到数据后，调用渲染函数将题目显示在屏幕上
        showTask(currentTask);
        
    } catch (error) {
        statusEl.textContent = `题目获取失败：${error.message}`;
    }
}

function saveScoreToLocal() {
    // 构造要保存的成绩对象
    // lastGameResult 包含了 耗时、准确率、时间戳 等信息
    if(!lastGameResult) return;
    // 本地持久化：保存到浏览器的 LocalStorage 中，防止刷新丢失
    const stats = getLocalStats();
    stats.push(lastGameResult);
    localStorage.setItem('neuroflex_stats', JSON.stringify(stats));
    // 远程同步
    // 将成绩异步发送给服务器端的 DataManager CGI 程序进行归档
    fetch('/cgi-bin/DataManager', {
      method: 'POST',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify(lastGameResult)
    }).catch(e => console.log('Data manager upload err:', e));
}
